> CLI 工具实战：一次从本地脚本到公开 npm 包的真实复盘。

先说结论：一个脚本能不能发布，不取决于 `package.json` 写得有多快，而取决于它出错以后，会不会收拾残局。

叶扬最近把一直在用的 CDP 网页截图脚本整理成了 npm 命令行工具。首个可用版本发布 `cdp-shot@0.1.0`，随后增加短命令 `cdps`，发布 `0.1.1`，最后补上 GitHub Release `v0.1.1` 和同名 Tag。

表面上看，只是把一条长命令缩短。实际走完才发现，命令入口只占很小一块，真正耗时的是兼容、异常清理、自动化测试和发布验收。

![从本地脚本到 npm CLI 的完整发布链路](/drafts/CLI%E5%B7%A5%E5%85%B7/assets/cdp-shot-npm/pipeline.png)

## 一、能跑和能交付，中间隔着一套契约

这个脚本原本就在本地工作流里干活：给知识卡片出图，给博客页面截图，按 DOM 元素取景。重复用到这个程度，继续复制脚本路径，已经开始拖累调用方。

叶扬有个判断：**一次性的事先做起来，预计重复三次以上的事，先建系统再放大。**

但“建系统”不等于马上换一个更大的框架。这次没有引入 Puppeteer 或 Playwright，而是保留原来的 CDP 调用。CDP 全称 Chrome DevTools Protocol，大白话就是：用浏览器自带的调试通道，指挥它打开页面、执行 JS、截一张图。

把内部脚本改成公开 CLI，有点像把一条只在本地跑的数据任务接成公共服务。输入格式要说清，失败要返回明确状态，临时资源要回收，老调用还不能突然死给你看。

照例戳破类比的洞：CLI 不是常驻服务，没有在线率指标，也不需要服务器值班。这个类比只在“边界变清楚了”这一层成立，不能拿服务运维那一整套往命令行工具上硬套。

## 二、第一刀不是发布，而是保住旧调用

首版定下的约束很朴素：单文件 CommonJS、零 npm 运行依赖、Node.js ≥22，原来的位置参数继续有效。

```bash
node ~/.claude/skills/screenshot/cdp-shot.js \
  https://example.com out.png 1440 900
```

npm 包的核心配置也不多：

```json
{
  "name": "cdp-shot",
  "bin": { "cdp-shot": "./cdp-shot.js" },
  "engines": { "node": ">=22" },
  "files": ["cdp-shot.js"]
}
```

这里有两条决策值得留下。

第一，**新入口不能拿旧入口祭天**。`cdps` 是短命令，`cdp-shot` 保留为兼容别名，仓库里的旧 `node` 调用也继续有效。

第二，**发布清单必须显式检查**。`files` 只放行脚本，npm 再自动带上 `package.json`、README 和 LICENSE。最终 tarball 只有 4 个文件，不包含 skill 手册、测试 fixture、PowerShell 脚本、浏览器 profile 或任何凭证。

给不熟 npm 的读者一句大白话：tarball 就是实际送进 npm 仓库的那只压缩包。仓库里有什么不重要，压缩包里有什么，才是用户真正会下载的东西。

## 三、卡壳角：最棘手的不是截图，而是关掉浏览器

截图主流程早就跑通了，发布前测试却连续揭出另一类问题：异常退出后，临时浏览器 profile 删不干净。

profile 是浏览器存放配置、缓存和登录态的目录。自动截图使用独立临时目录，退出时理应删除；用户显式指定的持久目录则必须保留。

Windows 上最怪的一次现象是：JS 异常路径已经结束本次浏览器进程树，递归删除也执行了，偏偏 profile 根目录持续报 `EPERM`。后台重试约 30 秒，目录还在。

继续查进程，没有发现那个 profile 对应的浏览器仍在运行。随后做了一个很小的对照实验：

| 操作 | 结果 |
|---|---|
| 对原目录直接 `rmSync` | 根目录持续 `EPERM` |
| 对同一目录先 `renameSync` | 重命名成功 |
| 对改名后的目录再 `rmSync` | 完整删除成功 |

![Windows 临时 profile 的 EPERM 排障对照](/drafts/CLI%E5%B7%A5%E5%85%B7/assets/cdp-shot-npm/windows-cleanup.png)

最后的修复不是更用力地杀进程，而是先把本次创建的临时目录改成一个唯一待删除名，再重试删除。异常和超时路径的测试随之恢复。

这个解法有边界：它只处理工具自己创建的独立临时目录，而且是在同一磁盘内改名。它不是 Windows 下删除一切 `EPERM` 目录的万能钥匙。

还有一条安全边界从头到尾没有动：只结束工具自己启动的 PID 和进程树，绝不按 `msedge.exe`、`chrome.exe` 映像名批量清理。否则截一张图，把用户日常浏览器也顺手送走，那就不叫自动化，叫添乱。

## 四、发布不是一条 npm publish

本地测试通过，只说明源码在这台机器上通过了。真正发布前，还要把交付物拆开验一遍。

这次实际走过的顺序是：

1. 用 `node:test` 和本地 HTTP fixture 跑真实 Edge，不依赖外网稳定性。
2. 检查普通截图、整页、元素 clip、CSS 替换、点击、暗色和持久 profile。
3. 用 `npm pack --dry-run --json` 核对版本和文件清单，并对照 `package.json` 检查命令入口。
4. 真正打一次 tarball，解包并运行包内 CLI。
5. 走分支、PR、squash 合并，再回默认分支复验。
6. 发布前确认包名、版本、npm 账号和公开权限。
7. 发布后用独立缓存执行 `npx`，验证 registry 里的实际产物。

`0.1.0` 最终是 **28/28 项测试通过**。测试数字本身不保证没有 bug，它只保证这批已写下的契约没有悄悄退化。

发布环节还遇到了一次 OTP。npm 要求身份验证器的一次性验证码，这一步由账号本人完成，令牌和验证码都不进 Git、不进文章。机器跑重复步骤，人拍板对外动作，这就是人在环上。

```bash
npm publish --access public
```

发布成功也不等于验收结束。还要从 npm 重新下载一次：

```bash
npx cdp-shot@0.1.0 --version
npx cdp-shot@0.1.0 https://example.com out.png 240 160 --scale 1
```

能显示正确版本，能生成尺寸正确的 PNG，才算闭环。

## 五、只缩短一个命令，也要发新版本

`0.1.0` 发布后，又有一个很自然的诉求：`cdp-shot` 还是有点长，能不能改成 `cdps`？

可以，但不能回头修改已经发布的 `0.1.0`。npm 的同一个版本不能覆盖重发，于是改动进入第二个 PR，版本号升到 `0.1.1`。

这次只加别名，不删旧命令：

```bash
cdps --version
cdp-shot --version
```

两个入口都指向同一个脚本。最终 **29/29 项测试通过**，实际 tarball 安装后，两个命令都验证过版本输出和真实截图。

现在全局安装只需要：

```bash
npm install -g cdp-shot@0.1.1
cdps https://example.com out.png 1440 900 --scale 1
```

免安装运行有一个小细节。包名是 `cdp-shot`，短命令是 `cdps`，所以不能简单写成 `npx cdps`，那会去查找名为 `cdps` 的包。正确写法是显式指定包：

```bash
npx --package=cdp-shot@0.1.1 cdps \
  https://example.com out.png 1440 900 --scale 1
```

版本号的价值就在这里：旧产物不动，新行为可追踪，问题出现时能准确回答“你运行的是哪一版”。

## 六、吵架现场：都有 npm 了，为什么还要 Release？

反方问题很合理：npm 能安装，GitHub 能看源码，再发 Release 是不是重复劳动？

答案是，三者各自管一层。

| 工具 | 管什么 | 不管什么 |
|---|---|---|
| npm 包 | 用户实际安装的运行产物 | 不负责讲完整发布背景 |
| Git Tag | 标记源码的某个版本点 | 本身不是安装包 |
| GitHub Release | 把版本、说明和源码归档放在一起 | 不替代 npm registry |

这次创建 Release `v0.1.1` 时，GitHub 同时创建了同名 Tag，不需要再重复打一次。

那 Assets 呢？很多项目的 Release 下面排着 Windows、macOS、Linux 的 exe 或压缩包，`cdp-shot` 为什么没有？

因为它不是编译成单个可执行文件的程序，而是一份跨平台 JavaScript。运行环境由用户本机的 Node.js ≥22 和 Chromium 系浏览器提供，同一份脚本走 npm 分发就够了。

![为什么这个 Release 不需要多平台 exe](/drafts/CLI%E5%B7%A5%E5%85%B7/assets/cdp-shot-npm/distribution.png)

只有目标变成“不装 Node.js，下载一个文件就能跑”，才需要引入各平台可执行文件的构建、签名和维护。对当前工具，那是额外成本，不是发布清单里的必选项。

## 七、这套流程可以搬走，但别只复制命令

如果把这次复盘压成一张清单，叶扬会留下这几项：

- 旧调用是否仍然可用？
- 参数错误是否有明确退出码？
- 成功、异常、超时、中断是否都回收资源？
- 测试是否验证行为，而不只是命令返回 0？
- tarball 是否实际解包运行过？
- 是否从 registry 独立下载验收？
- 版本、Tag、Release 是否指向同一次交付？
- 凭证和对外发布是否仍由人拍板？

请记住这句判断，后面所有决策都是从它推出来的：**发布不是把文件换个地方，而是把“在我这里能跑”改成“别人拿到以后，知道它会怎样运行，也知道它会怎样失败”。**
