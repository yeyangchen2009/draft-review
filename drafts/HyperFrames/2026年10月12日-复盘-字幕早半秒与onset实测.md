做 hf-01 的时候，叶扬第一次在粗剪里撞见这个毛病：画面底部的字幕条「啪」地亮了，可解说的声音还没到，要再等那么一小会儿，那句词才从耳机里冒出来。

一小会儿是多久？他当时的回答是：「说不上来，反正差一点。」

等做完三集 HyperFrames 教程再回头看，这个「差一点」有了精确的名字——**平均 0.28 到 0.38 秒，因片而异、因测量口径而异**。这篇复盘讲的就是一件事：一个肉眼肉耳只能定性的同步问题，怎么被拆成可测量、可复现、可以放心写进参数里的数字。

## 一、先排除所有想当然

字幕时间戳来自 faster-whisper 的转录，经过对齐脚本写进 `cues.json`，渲染器按时间戳控制整句淡入和逐字变色。链路不长，嫌疑犯却不少：是不是 TTS 开头吃字？是不是播放器有延迟？是不是淡入动画做得太慢，让人误以为字幕早了？

叶扬先在对齐脚本里有个微调量 `word_lead`，意思是「每个词的时间戳整体提前一点点」。他试着推这个旋钮：+0.08、−0.1，来回折腾，每改一次就重新对齐、重新渲染、再戴耳机听一遍。结果是——**每一遍都还是「差一点」，只是差的方向变了**。手感这个东西，没法当反馈信号用：你听三遍同一段，会得到三种判断。淡入动画也被列为嫌疑人查过，办法是直接抽帧：在句首时间戳那一帧把画面截出来，字幕条确实已经亮了——和动画快慢无关，它就是「按点上班」的，问题出在这个「点」本身。

旋钮失灵，说明根因不在词级对齐的精度上。词级再怎么微调，动的都是句子内部的相对节奏，可这个毛病是**每一句整体往前错了同样的一截**，属于坐标系问题，不属于表走得快慢的问题。问题比这更靠上游：他需要先回答「字幕到底早了多少」，才有资格谈怎么修。

## 二、onset 配对法：让音频自己招供

思路很朴素。句子和句子之间有停顿，这是天造地设的测量点：停顿一结束，就是那句词真正开口的时刻，行话叫 **onset（发声起点）**。把全片的 onset 都找出来，再跟 `cues.json` 里的句首时间戳两两配对，一减——

```
偏差 = 真实发声时刻 − 字幕句首时间戳
```

正数，说明字幕早于声音；负数，说明字幕晚了。

找 onset 不用写信号处理，ffmpeg 自带 `silencedetect` 滤镜，它会把每段静默的起止时刻打到日志里：

```bash
ffmpeg -i media/audio.wav \
  -af silencedetect=noise=-48dB:d=0.08 -f null -
# 日志里逐行出现：silence_end: 8.365
```

`n=-48dB:d=0.08` 的意思是：电平连续 0.08 秒低于 −48dB 就算一段静默，静默结束的那一刻就是 onset。然后 Python 做配对，关键是**一个 onset 只配它前面最近的那个句首，不争不抢**：

```python
import bisect, re, subprocess, json

cues = [c["s"] for c in
        json.load(open("cues/cues.json", encoding="utf-8"))["cues"]]
log = subprocess.run(["ffmpeg", "-i", "media/audio.wav",
    "-af", "silencedetect=noise=-48dB:d=0.08", "-f", "null", "-"],
    capture_output=True, text=True).stderr
onsets = [float(m) for m in re.findall(r"silence_end: ([\d.]+)", log)]

diffs = []
for o in onsets:
    j = bisect.bisect_right(cues, o) - 1   # 前面最近的句首
    if j >= 0 and o - cues[j] < 0.6:       # 0.6s 配对窗
        diffs.append(o - cues[j])
```

十几行代码，一个玄学问题当场变成一张统计表。

配对规则里有两个细节值得说。第一是 **0.6 秒的配对窗**：onset 只跟 0.6 秒之内的句首配，超出就丢弃。停顿偶尔会特别长，或者某句话说得含糊、门限没识别出停顿，这时硬配只会产生脏数据，不如让这个点空着。第二是「不争不抢」：用 `bisect_right` 保证一个 onset 只配它前面最近的那一个句首。早先的版本试过「每个句首找最近的 onset」，结果密集段落里两个句首会抢同一个 onset，偏差分布立刻被搅浑。另外全片第一句话前面没有停顿，天然测不了，hf-02 的第一个 cue 就因此排除在外——这也是为什么配对数永远少于句数。

## 三、根因：停顿被 Whisper 吃掉了

三集测下来，偏差齐刷刷地落在 +0.27 到 +0.39 秒，几乎没有负值。**系统性地全早，而且早得很稳定**——这不是随机误差，是结构性错误。

对着 `raw.json` 里 Whisper 的原始分段一看就明白了：它给出的段落，起点经常死死贴在上一段的终点上。句间那两三成秒的停顿，没有被记成「上一段结尾的留白」，而是被**吞进了下一段的开头**。于是下一段的时间戳戳在了停顿开始的地方，可真正的发声在停顿结束之后——字幕提前亮起，提前的量正好就是停顿的长度。

更麻烦的是，这个量在连续说话的段落内部近似恒定，所以光靠肉眼对某一句，你永远估不准：每句都早差不多的量，没有参照系。只有把几十个停顿点摊在一张表里，那个稳定的偏移量才自己浮出来。

## 四、复盘日的一场小惊吓

写这篇复盘前，叶扬想把三集的数据复测一遍，好让文章里的数字都能现跑现验。hf-01、hf-03 都对得上，偏偏 hf-02 出了鬼：当年入片用的是 **46 对配对、中位偏差 0.373 秒**，可这次用上面那套 −48dB 的法子跑，只剩 28 对、中位 0.273 秒。

0.1 秒的出入，足以让任何一篇复盘当场报废。他没急着怀疑当年测错，先去翻了当时的命令记录——还好，终端日志还在。一看，问题出在「静默」的定义上：

- 当年 hf-02 用的是 **`-30dB:d=0.3`**：只认又长又安静的大停顿，声音必须涨响到 −30dB 才算「开口」，全片 58 个停顿点；
- 这次复测用的是 **`-48dB:d=0.08`**：门槛低得多，气声、辅音一冒头就触发，只有 37 个点。

silence_end 是电平**越过门限的那一刻**报出来的。门限定得高，就得等声音从第一丝气息涨响到正常音量才触发，自然要晚个 0.1 秒——0.373 和 0.273 都对，它们量的是同一次开口的两个不同事件：**第一可闻声**，和**声音真正立起来**。

把三集按两种口径各跑一遍，结果整齐得像做过实验设计：

| hf-01《认识 HyperFrames》 | 133 | 23 / 285ms | 24 / 382ms | 0.28s |

| hf-03《第一个 clip》 | 176 | 33 / 295ms | 52 / 387ms | 0.29s |

复测时还做过一次参数扫描给自己吃定心丸：门限从 −45dB 扫到 −52dB、最短停顿时长从 0.05 扫到 0.08 秒，低门限这一口径的中位数始终钉在 273 到 278 毫秒之间。换句话说，**数字对参数不敏感**，它不是调门限调出来的巧合。会搬动数字的只有「你到底想对齐哪个声学事件」这一个选择——这正是口径二字的分量。

这张表顺便揭了个当年没意识到的底：**三集的偏移其实几乎一样，0.28 和 0.37 的差距主要来自测量口径，而不是片子本身**。hf-01、hf-03 量的是「第一可闻声」，取 0.28、0.29；hf-02 量的是「声音立起来」，取 0.37。两种对齐都说得通——字幕贴着第一丝声音走，还是贴着元音真正响起来走，差异只有约 0.1 秒，远在人眼能察觉的边缘以内。但口径必须写在数字旁边，否则连作者本人三个月后都会被自己的数据吓一跳。

还有一个坐标坑：测量必须在**正片母带**上做，不能在最终成片上做。hf-02 的成片前面有 2 秒封面静帧，声轨整体后移了 2 秒；要是拿成片跑 silencedetect 再跟母带时间轴上的 cue 配对，每个偏差都会凭空多出 2 秒，统计表会当场变成抽象画。

## 五、修法：一个参数，整体平移

根因是系统性的恒定偏移，修法就不该是词级的缝缝补补。最终方案是一个参数 `time_offset`：整句淡入的时间轴和逐字变色的时间轴，**全部整体向后平移**。

```python
# make_video.py 底部字幕轨道
# 真实发声落后句首时间戳：按本片 onset 实测中位数取值
frag = char_track(cues, chars, THEME.accent, time_offset=0.37)
```

三集分别传 0.28、0.37、0.29。平移之后再抽帧、再听，残余偏差都压在 70ms 以内——大约两帧，属于「机器知道、人不知道」的范围。那个调来调去怎么都不对的 `word_lead`，直接废弃。

## 写在最后：测量最容易丢的东西是「口径」

这件事真正的教训不是「字幕要延后 0.3 秒」——那只是结论，抄走也没用，换个 TTS、换个 ASR 模型可能就变了。真正值钱的是三条：

1. **「差一点」不是反馈，分布才是。** 人耳对单次偏差的判断不可复现，但几十个停顿点的中位数不会骗你。凡是同步类的玄学问题，先找天然的基准事件，再配对、再看分布。
2. **先测再定值，每片一测，不抄作业。** 参数写死在代码里的底气，来自它对应一次真实测量；测量脚本留在项目里（hf-03 的版本在 `oneoffs/measure_offset.py`），下一集开工第一件事就是让它跑一遍。
3. **数字必须和口径绑在一起存档。** −48dB 量出的 0.27 和 −30dB 量出的 0.37 不是矛盾，是两个问题的两个答案。这次靠翻终端日志才洗清的惊吓，已经记进流程：测量脚本的门限、窗长、配对规则，和中位数写在同一行输出里。

工具链里这类「手感参数」其实还有不少。叶扬现在的习惯是：每撞上一个，就逼自己问一句——「它能不能变成一个 onset 配对实验？」能，就花二十分钟把它变成数字；不能，再承认它是艺术。

目前为止，投降的次数不多。
