hf-04《灵魂在 seek》成片那天，叶扬本来以为最难的部分已经过去了：F2 复查的 57 个疑点逐条过清，check 零错误，26 幕 313 句时间轴钉死。按下 render，去倒杯水等收片。

水还没喝完，终端红了一片：33 路视频抽帧，崩了 16 路，正好将近一半。

这篇复盘讲两件事。第一件是这次崩盘面的真凶——一个叫 VFR 的东西，怎么把 gdigrab 录屏的时间戳抖动一路传进渲染器，最后靠三个 ffmpeg 参数根治；第二件是成片之后 F2 揪出的一个「深色浮层穿帮」疑点，怎么不靠肉眼吵架、而是用一块 1000×130 像素的亮度取证区把它证伪。一个是机时税，一个是方法论，都是这集新长出来的教训。

## 一、首轮 render：33 路抽帧，崩了 16 路

先说「抽帧」是什么。这集有 33 段录屏素材要嵌进页面：Notepad++ 写代码、Edge 演示、终端跑命令。渲染器不能直接把 mp4 塞进逐帧截图的流水线，得先把每段视频按 30fps 解成一张张 PNG——33 段合计 7142 帧——无头 Chrome 渲染到对应时刻时，把那张 PNG 当背景贴上去。

第一轮 render，日志里抽帧阶段大批报错。叶扬起先怀疑是内存：这台机器没有独显，沙箱还限内存。但翻栈发现 16 路死法高度一致，全都死在同一条支路上——渲染器的 **VFR 慢速支路**。

要理解这条支路，得先认识两个帧率口径。用 ffprobe 看一个正常视频，有两个字段：

- `r_frame_rate`：标称帧率，也就是这文件「声称」自己是多少帧每秒；
- `avg_frame_rate`：时长除以总帧数算出来的实际平均帧率。

正常视频两个数都是 30。而这批 gdigrab 录屏精切出来的小片段，标称帧率端端正正写着 30/1，实际平均帧率却从 5 到 24 不等。渲染器预检时算一笔账：

> |rFps − avgFps| / max(rFps, avgFps) > 0.1

两个口径差超过 10%，就判定这是 **VFR**（可变帧率）文件。普通支路喂帧会错位，于是切到慢速支路：先把视频解成 rawvideo、经一个 NUT 容器管道喂给第二个 ffmpeg，再逐帧落盘。这条慢路本身没错，错在它被触发时没有并发上限——33 段视频各自起一对 ffmpeg 进程，`Promise.all` 一口气全放出去，rawvideo 是不压缩的，每路瞬时吞上 GB 内存。无独显的办公本当场被挤爆，16 路被操作系统杀掉。

![上轨示意 gdigrab 帧到达忽密忽疏、平均帧率掉到 5-24fps；下轨加 -vf fps=30 后帧帧等间隔；右侧红卡是 VFR 判据与 33 路崩 16 路，绿卡是二轮 33/33、vfrPreflightCount=0](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04-review/hf04r01-vfr.png)

## 二、真凶：gdigrab 的 PTS 抖动

为什么录屏会变成 VFR？源头在 ffmpeg 的 gdigrab：它按屏幕变化抓帧，帧的时间戳（PTS）来自系统桌面调度。桌面忙、GPU 忙、磁盘忙的时候，两帧之间就不止 1/30 秒；闲的时候又贴得很近。录出来的母带还是 30fps 的壳，时间戳已经在抖。

hf-03 用的是同一套录屏工艺，为什么没炸？因为那集只有 13 段素材，数量少、每段短，精切之后偏移量没有越过 10% 那根线，预检全部放行走普通支路——**不是工艺没问题，是规模没到**。hf-04 素材量翻到 33 段，抽签抽中了。这种「上次侥幸、这次翻倍还债」的 bug，比稳定复现的 bug 值钱：它逼你把根因挖出来，而不是重启碰碰运气。

## 三、根治：三个参数，二轮 33/33

修法落在精切脚本 `cut_shorts.py` 的编码参数上，核心就一个滤镜：

```bash
-vf fps=30
```

这行的作用不是简单地「指定帧率」，而是在过滤链里**重建时间戳**：解码后的帧经过 fps 滤镜，被重新打上等间隔的 PTS，忽密忽疏的帧流被重采样成严丝合缝的 30fps。出来之后 `r_frame_rate` 和 `avg_frame_rate` 都是 30/1，预检那笔账算出来是 `|30−30|/30 = 0`，走普通支路。

顺手又补了三个参数：

```bash
-g 30 -keyint_min 30 -movflags +faststart
```

`-g 30` 让视频每秒至少有一个 IDR 关键帧。母带是「稀疏关键帧」文件——关键帧间隔可能几十秒，当时只知道它让 compile 阶段刷一行 sparse keyframes 警告；没想到后来人工抽帧复查时，这个特性又坑了叶扬一次（后面讲）。`+faststart` 把 moov 元数据挪到文件头，浏览器起播更快。

二轮 render，全程 52 分钟，一次过：抽帧 33/33 成功，`vfrPreflightCount: 0`，`extractedVideoCount: 33`，`totalFramesExtracted: 7142`。

教训固化成一条工艺铁律：**凡是录屏母带精切出来的片段，必须 `-vf fps=30` 强制 CFR，没有例外。** 标称帧率是可以撒谎的，信 r_frame_rate 不如信 avg_frame_rate，最稳的是直接把时间戳重打一遍。

## 四、52 分钟机时账：税都收在截图上

二轮跑的时候叶扬掐了表，五个阶段各花多少秒，账很清楚：

![横向耗时条：capture 无头 Chrome 逐帧 seek 加截图 2815.6 秒即 46 分 56 秒独占红色长条，audio 118 秒、extract 91.1 秒、assemble 77.6 秒、compile 14.8 秒；合计 52 分 03 秒，capture 占 90.2%](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04-review/hf04r02-render-time.png)

页面编译 15 秒，33 段抽帧 1 分 31 秒，口播母带处理 1 分 58 秒，FFmpeg 烤片合成 1 分 18 秒——加起来不到五分钟。剩下 46 分 56 秒，占总机时 **90.2%**，全在 capture 阶段：无头 Chrome 加载页面、把时间轴 seek 到每一帧、等 GSAP 摆位、截图。总帧数 18195（7142 帧素材抽解＋合成口型页），一张一张截，single-worker 串行，ANGLE 走 D3D11 软件回退——Intel UHD 620 核显扛 1920×1080 的页面合成，没有任何捷径。

这笔账直接改变了后面的工作排序：**改一句文案、挪一个元素，重烤一次就是 47 分钟起步。** 所以文字复查、F2 逐帧疑点、时间轴核对，全部必须压在 render 之前完成。渲染不是调试工具，是发行工序——这跟正经软件项目里「集成测试最贵，所以单元测试左移」是同一个道理，只不过这里的集成测试一次要跑将近一小时。

## 五、F2 最后一个疑点：296.10 秒的「深色浮层」

片子烤出来，F2 二轮复查沿时间轴逐点扫，57 个疑点过掉 56 个，最后卡在终片 296.10 秒：画面上 Notepad++ 窗口的代码区上方，压着一个半透明深色长条，形状规整、边缘利落，怎么看怎么像一个**不该出现的 HTML 浮层穿了帮**——渲染器最擅长出的就是这类事故。

![左：终片 296.10 秒，深色卡压在浅绿代码区上，金色框标出 ROI；右：296.50 秒切到同源 freeze，卡片已离场，画面连续](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04-review/hf04r04-fadecard.png)

叶扬没有立刻下「穿帮了、重烤」的结论。47 分钟一次的返工，值得先花十分钟做分层排查。先把画面拆开：这一段在时间轴上是两个素材拼接——290.20 到 296.20 秒是录屏视频 `gsap-paused.mp4`，296.20 秒起切换到同源 freeze（静帧）。可疑深色条完全出现在视频段内部，不是接缝处的合成事故。那么候选只剩两个：

1. 页面上有个 HTML 覆盖层，渲染时压在了视频之上——这是真事故；
2. 深色条是**录屏内容本身**——Notepad++ 里的自动补全弹窗、或者演示页面里的元素，那就是素材的一部分，不是缺陷。

先查页面源码：这一幕确实有一个 `#g1-card`，但它是演示页里的概念卡片，深色 `#18181b`、不透明，按时间轴设计在第 296 秒淡出。再对照分镜脚本：296 秒前后讲的正是「paused 的卡片离场」。嫌疑开始反转——那个「浮层」会不会就是这张卡片本身？

## 六、抽帧先踩了 sparse keyframes 的坑

取证要先把关键帧抽出来看。叶扬顺手用最常用的 input seeking 写法：

```bash
ffmpeg -ss 296.10 -i hf-04-yeyang-cover.mp4 -frames:v 1 shot.png
```

抽出来一看，画面内容根本不是 296 秒——是 22.5 秒的开场。原因前面埋过：终片是 sparse-keyframe 文件（每秒关键帧的修复只作用在精切小片段上，终片烤片时关键帧间隔又被拉长了）。input seeking 在这种文件上会退化成关键帧 seek，落点退回到更早的关键帧，`-ss` 形同虚设。换成 **output seeking**——`-ss` 写在 `-i` 之后，从头解码到指定时刻——才拿到精确帧。代价是慢：606 秒的片子，深位置的一帧要解三四十秒。循环批量抽时还得加 `-nostdin`，否则 ffmpeg 的交互解析器会吞掉后续输入。

296.10 秒和 296.50 秒两帧并排（上图），事实清楚了：深色条是一张写着代码的深色卡片，正在向上淡出；0.4 秒后它完全离场，底下浅绿代码区干净露出，画面连续，没有任何拼接痕迹。它就是 `#g1-card`。

## 七、ROI 亮度取证：让像素自己说话

目检能定性，但叶扬还想要一条铁证：如果深色卡是按 GSAP 时间轴设计淡出的，那么它的透明度变化必须与时间轴指令**逐帧吻合**。于是用 signalstats 滤镜在卡片覆盖的区域取了一块 ROI——Notepad++ 第 2 到 4 行浅绿代码区，坐标 (280,185)、1000×130 像素——逐帧导出平均亮度 YAVG：

```bash
ffmpeg -i hf-04-yeyang-cover.mp4 -ss 290.20 -t 10.0 \
  -vf "crop=1000:130:280:185,signalstats,metadata=print" -f null -
```

（一个小坑：`metadata=print` 的输出是 info 级日志，加 `-loglevel error` 会被压得一行不剩。）

300 个采样点画成曲线，结果漂亮得像教科书：

![ROI 亮度曲线：video 段 YAVG 在 47 平台（深色卡不透明覆盖），296.00 到 296.35 爬升宽 0.35 秒，296.20 绿虚线处切同源 freeze，之后 192 平台、接缝两侧零跳变](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04-review/hf04r03-roi.png)

- 296.00 秒之前，ROI 亮度钉在 **YAVG ≈ 47** 平台——深色卡不透明地盖在浅绿代码区上（300 帧最小值 46.9986）；
- 296.00 到 296.35 秒，亮度单调爬升，爬升段宽度不多不少 **0.35 秒**，正好等于时间轴里的指令：

```js
tl.to('#g1-card', { opacity: 0, duration: .35 }, 296.0)
```

- 296.20 秒那条绿色虚线是视频切 freeze 的接缝，两侧亮度同为 **192**（300 帧最大值 192.614），零跳变——接缝两边的画面本来就来自同一个瞬间；
- 之后稳定在 192 平台，那是浅绿代码区的本来亮度。

曲线的每一级台阶都能对上一条时间轴指令：47 是覆盖、0.35 秒爬升是淡出、192 是离场。**浮层不存在，穿帮不存在，存在的是一张严格按设计演出的卡片。** 疑点闭环。

## 八、这集新长出来的三条规矩

第一条，**疑似穿帮，先分层再定性**。画面是多层合成的结果——录屏视频、HTML 覆盖、freeze 接缝、字幕轨道，各有各的来源。先问「这东西属于哪一层」，再问「这一层该不该有它」，最后才问「要不要返工」。看到异常就喊重烤，47 分钟一次，谁也扛不住。

第二条，**能用数据证伪的，不靠肉眼投票**。「像不像浮层」是主观争论，YAVG 曲线是不是 0.35 秒爬升、接缝两侧跳不跳变，是客观事实。FFmpeg 的 signalstats、crop、metadata 三件套加上几十行解析脚本，十分钟出铁证。这次它洗清了一个冤情，下次也可能坐实一个真 bug——工具不预设立场，这正是取证工具该有的样子。

第三条，**录屏精切必须强制 CFR，抽稀疏关键帧的片必须 output seeking**。`-vf fps=30` 进精切工艺，`-ss` 放 `-i` 之后、循环里加 `-nostdin` 进取证工艺。hf-03 的 13 段是侥幸，hf-04 的 33 段是还债；把还债的利息写成规矩，hf-05 才不用再还一遍。

F2 的 57 个疑点是人眼防线，ROI 的 300 个亮度点是像素防线。两道都过了，这集才敢点发布。后来片子顺利上线——回看这一天，崩掉的那 16 路和那块「不存在的浮层」，其实都是来送经验的：一个告诉你规模会放大侥幸，一个告诉你证据要取到像素级。

下次 render 之前，叶扬大概会先看一眼精切参数，再去倒那杯水。
