10 月 19 日晚上九点半，叶扬做了一个很贵的决定：换掉这集片子的事故主角。

那时探针做完、稿子写完、蝉镜配音合成完、cues 对齐完、封面截完，连录屏素材都拍完一半了。像素证据表明，全片围绕着转的那个「seek 不到的动画」，找错了对象。这一篇讲这次中期翻案的全过程：最初的判断从哪来，证据怎么翻的案，黑户长什么样，以及 2.5 小时和 11 段重合成的代价具体花在哪。

## 一、探针：一台命令一台命令试出来的事实矩阵

事情开头并不冒进。hf-04 的计数器事故之后，叶扬对「preview 是活的、烤片是死的」这类故事保持着高度警惕，所以这集立项后第一件事不是写稿，是给 HyperFrames 0.8.107 的五条查帧命令做前制探针（PR#175，10-19 上午 11:50）：preview、snapshot、keyframes、compare、grade-compare，逐条在真机上跑，配三个种子页，把每台命令的真实输入输出、报错文案、静默行为落进 PROBE-NOTES。

探针要回答的核心问题是：什么样的动画，preview 看着对、snapshot 定不住？最初的假设带着明显的 hf-04 惯性——GSAP 有 timeline 契约、有 window.__timelines 注册表，seekable 是明媒正娶；CSS keyframes 动画是浏览器自己跑的，没有注册到渲染器的时间轴上，那它凭什么听 seek 的？探针笔记据此把「不可定位事故」押在了 CSS keyframes 身上：网页里最常见的写法，恰好是烤片炉里最可能失控的写法，这个叙事也漂亮。

漂亮的假设最危险。后面的事证明，探针这一步只完成了「命令事实矩阵」，没完成「事故像素矩阵」——命令怎么调用查清楚了，但事故到底在谁身上，纸面上的归类要等真机彩排才见分晓。

## 二、布景：三个工程冻结，12 个 case 像素彩排

录屏工程不是一个，是三个，外加一个变体，10-19 晚全部冻结（PR#179/#180）：

- **蓝块**：GSAP 从左滑到右，登记在册的 seekable 对照组；
- **绿点**：class 名 legalPulse，最普通的 CSS keyframes 喘气动画，嫌疑人；
- **红块**：setInterval 驱动，闭包里一个自有计数器，4 秒走完全程；
- **红块 v3 慢表**：同一段脚本，表调慢到 60 秒一圈，专做边界实验。

布景脚本带 prenormalize 归一化和 backup 哈希闸，每次 restore 到指定权威状态后先哈希后开拍，防止布景漂移污染证据。录制排了 9 个 take，guard 窗口白名单和 cdp 机位两条安全锁沿用 hf-05 的规矩。

彩排一共 12 个 case，全部是像素断言，不靠眼看大概：蓝块在同一秒连拍必须同位；绿点同秒连拍必须同相位；红块同秒连拍 distinct 位置不少于 3 个；`#bad` 在 keyframes 报告里必须隐身；对 `#bad` 打 `--shot` 必须出硬报错。等待常量按第七次彩排的热态耗时乘 1.3 留余量。

## 三、翻案：绿点四帧钉死，红块四帧四个位置

12 个 case 跑下来，押在 CSS 上的假设当场破产。

绿点——那个写在 `<style>` 里、浏览器自己调度、从没跟渲染器打过招呼的 CSS keyframes——在同一秒的四张 snapshot 里钉死在同一个相位，一寸没挪。机制不复杂：现代浏览器内部有统一的 Web Animations API，CSS keyframes 动画和 WAAPI 动画走同一条时钟，渲染器无头浏览器 seek 文档时间，CSS 动画一并被接管。「不注册 __timelines 就 seek 不到」是叶扬把 GSAP 的私有契约错当成了行业门槛——人家浏览器自带户口，不用上渲染器的户口。

真正四帧四位置的是红块。回头看它的脚本，四条规避占全了：不注册 window.__timelines，不经过 WAAPI，不读 Date.now 或 performance.now，不用 requestAnimationFrame。它就是 setInterval 加闭包计数器，只认真实过了几秒。渲染器把文档时钟拨到第二秒拨四次，对它毫无意义——四次按下快门的墙钟瞬间不同，计数器走得不一样远，红块就站在四个地方。

![同一秒钟连拍四张的接触表：蓝块四帧同位、绿点四帧同相位、红块四帧四个位置，这张图同时完成了对 CSS 的平反和对 setInterval 的定罪](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf07-review/hf07r01-contact4.jpg)

更刁的是 check 的态度。这段脚本要是敢直接读系统时间，或者用 rAF 那种逐帧回调，StaticGuard 立刻拦下；它偏不碰任何时间 API，关起门来记数，check 就查不出一点毛病——preview 顺滑、check 全绿，只有 snapshot 露馅。这让它成为一个比 hf-04 计数器更纯粹的教学标本：hf-04 的事故还读了时间，这一个连时间都不读。

## 四、黑户三连：报告里没户、点名叫不应、洋葱皮没残影

定了主角之后，给红块取证反而异常顺利，三条证据在彩排时全部固化成可拍的命令输出。

**第一连，体检报告没这一户。** keyframes 不加 `--shot` 参数是逐户登记模式：GSAP 动作、CSS keyframes、Anime 时间线，一户一户列出来。工程里报告明明白白三个 items——蓝块、时钟、绿点——红块明明在画面里动，报告上压根没有它。

**第二连，点名叫不应。** 对红块直接打 `keyframes --shot '#bad'`，机器不糊弄一张空图，反手一个硬报错：这个选择器下面没有动画在动，离得最近的三个动画元素是 `#good`、`#clock`、`#legal`。它在动，机器却不知道它在动——终端红行被 freeze 成一帧，成了片里最有说服力的一张屏录。

![终端硬报错：上半 keyframes 体检报告列出 v1 - 1 item 登记户，下半「--shot: nothing animates under '#bad'. Nearest animated elements: #good, #clock, #legal.」](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf07-review/hf07r01-kfbad.png)

**第三连，洋葱皮没残影。** `--shot` 对登记户拍的是轨迹洋葱皮：沿线采九个点，半透明残影排在时间线上，蓝块九帧轨迹清清楚楚，拐弯、停顿一眼看完。洋葱皮也公道，只画登记过的运动——红绿两个连残影都没有。

![onion 洋葱皮：蓝块九帧轨迹从 0s 排到 10.5s，青到紫渐变，右侧红蓝两框叠在终点；画面左下红块脱离时间轴单独标注「墙钟」](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf07-review/hf07r01-onion.png)

## 五、慢表：一分钟一圈的边界实验

翻案之后叶扬补了一个边界实验，把「seek 管不着」从定性推到定量。红块 v3 的表调慢到 60 秒一圈，再让 snapshot 停在第十秒：蓝块 8 秒走完全程，早贴在右端终点；红块的表才走了六分之一，还贴在起点附近。

![慢表实验 t=10.00s：蓝块 OK 已到右端终点，红色「慢表」块还贴在左下角起点；字幕写「自掐表动画，慢表一分钟一圈（seek 照样管不着）」](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf07-review/hf07r01-slow10.png)

这张图堵死了一种和稀泥的解释：也许四帧四位置只是节拍相位问题，凑齐了总能对上。慢表实验说明，seek 给出的时间和红块自己的表是两条互不相干的轴——表快表慢、定在第几秒，两者之间没有任何函数关系。配合正片里那句「同一个第几秒，不管求多少次，答案必须是同一个」，seekable 的定义被边界实验钉死了：不是「大部分时候对得上」，是任意时点、任意次数求帧，结果唯一。

## 六、翻案的账单：2.5 小时，11 段，440.17 秒到 559.22 秒

决定换主角是 10-19 晚 21:34，重制在 10-20 上午 09:34 落地（PR#183）。成本逐项记账：

**稿子**：src 21 段扩成 22 段、2276 个汉字。三元素布景段重写，墙钟段重写，新增慢表 60 秒边界段；CSS 整个平反——绿点从反面教材变成「合法 CSS 动画」的证人；体检段改成三 items 加 `#bad` 隐身加硬报错；grade 段顺手加了 inactive/no-op 的料（之二细讲）；结尾总结和行动件从「提防 CSS」改成「不登记时间轴、自己掐表跑的动画留给网页，别留给烤片炉」。写稿时同步避音：数 shǔ 改成累加/记数，得 děi 改成「要按」，当 dāng 改成立刻；make_tts 的计数闸回填（行 1、得 6、还 8、地 5、数 9，`--shot` 从 3 处变 4 处）。

**配音**：22 段里 11 段在蝉镜网页试听通道重合成（seg02/04/07/08/09/12/15/16/18/19/20），试听 0 蝉豆。新建 rebuild_audio.py 做段级重建：旧段按 cues 边界加静音谷点切窗——共享时间戳处如果取中点会腰斩尾音，这是实操中踩出来的；新旧段之间统一 0.14/0.20 秒停顿。旧母带备份为 hf-07-yeyang-old-css.wav（440.17 秒），新母带 **559.22 秒、22 段**，片子长出近两分钟，主要是慢表实验和黑户三连的新内容。

**对齐**：transcribe 和 cues 全部重跑，**273 句**，匹配率 OK 90.4%、音近 8.9%、GAP 15、0 个字形 fallback；time_offset 从旧版双峰裁决的 0.29 重测为 **0.31**（中位数 +315 毫秒）。

**封面**：v1 封面的图例还写着「CSS 墙钟·四帧四位置」，与成片直接矛盾，finalize 前的抽帧闸抓住，重做（之三细讲）。

合计约 2.5 小时净投入，外加 11 段蝉镜合成的等待墙钟。全部花在「把一个已经做完的决定改对」上。

## 收尾：像素断言的级别

这一集买到的头条规矩，是探针笔记里那句话的升级版：**教学事故必须在真机布景上用像素断言验证到「seek 不可定」级**。

「命令事实矩阵」证明的是工具怎么用，纸面归类证明的是假设讲不讲得通——两者都不构成事故成立的证据。绿点和红块在 preview 里同样顺滑，在 check 前同样全绿，唯一让它们分高下的是同一秒四张照片的像素：同位还是异位，这是二元判据，没有商量空间。12 个 case 的彩排贵在录制之前，但比起 11 段重合成，它便宜得像白送；真正贵的是这次只做了命令探针、没在写稿前把事故像素也跑齐——彩排虽然翻了案，翻案点却落在了稿、音、封面全部完工之后。

下一篇离开主角，讲这集另一起事故：调色工具静默 no-op，三格画面一模一样，机器其实发了警告；以及代录首跑为什么 12 次彩排全绿、t02 一开拍却连崩两个 bug。
