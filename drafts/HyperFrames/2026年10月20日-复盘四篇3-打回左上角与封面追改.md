主角翻案、调色修复、素材精切全部落定之后，10-20 上午进入分镜。20 个幕从三元素实验台排到 render 预告，10 段屏录 shorts、2 段终端红行 freeze、若干 artifacts 实拍 PNG 全部按精切的实际媒体名和时长挂载。首轮 snapshot 抽帧就抓出两个真 bug——一个 CSS 特异性，一个 gsap.from 的新变体；finalize 前的抽帧又抓住封面一个与成片直接矛盾的事实错误。这一篇讲这三处，以及为什么三处全靠「看照片」而不是 check。

## 一、双类同特异性：源码在后的 left:0 赢了

右卡是这集常用的版式：屏幕右侧出一张概念卡，配合左侧终端画面讲事。定位由 `.gk` 类负责（`left: 1200px`，把卡片送到右半屏），视觉由 `.rightcard` 类负责（背景、边框、圆角、阴影）。同一个元素挂两个类，各管一摊——写完看 preview，卡片在该在的位置；首轮按拍点抽 snapshot，右卡集体消失，放大一看，全挤在屏幕左上角，left 归零。

机制是 CSS 选择器特异性的老规矩：`.gk` 和 `.rightcard` 都是单类选择器，特异性相等；相等时，**样式表里源码靠后的规则赢**。`.rightcard` 的规则当初是从旧卡片连写拷过来的，视觉声明里带着 `position: absolute; left: 0;`——本意是给左卡一个默认锚点，合写在视觉类里一直没拆。样式表中 `.rightcard` 又恰好在 `.gk` 之后，于是每一张右卡都被 `left: 0` 拉回左上角。preview 没暴露，是因为卡片大多带着入场补间，活动画面里注意力被动画牵走；snapshot 拍的是入场完成后的静态帧，位移无处可藏。

修法是把规则按职责拆源：**定位只由 `.gk` 提供，`.rightcard` 只保留视觉声明**，连写块里的 position 和 left 全部删走。一条规矩跟着固化下来：一个类要么管布局要么管皮相，合写规则就是给未来的同特异性对决算伏笔；新增第二个类之前，先 grep 旧类里有没有藏着定位声明。

## 二、gsap.from 新变体：只对子元素 from，容器先以空框亮相

第二个坑是 gsap.from 的，而且是系列第一次见到的变体。

hf-04 时期结过一条案：纯 `gsap.from` 不用预先把元素藏起来——from 会立即渲染目标态，预置隐藏反而会闪。这集的三处场景（onion 洋葱皮、sneak 黑户三连、present 工具卡）换了个结构：**容器自身没有任何补间，补间只加在它的子元素上，而容器自带不透明背景和边框**。时间线一播放，子元素还停在 from 的起点（透明度 0、位移未归位），容器本身却已经在场——于是场景开头先亮出一个空荡荡的深色描边框，悬在屏幕上等半秒，内容才从框里长出来。

旧结论不管用的原因就在结构差：那条结论保护的是「被 from 的元素自己」，管不到「没被 from、却包着 from 元素的容器」。补间树和 DOM 树不是一棵树，子元素的初始态不会替父元素向渲染器请假。

修法：三处容器各补一个 `fromTo` 控制 opacity，在子元素入场前 0.2–0.6 秒把容器从 0 淡入——提前量按每个幕的节奏单独定，让边框出现和第一批内容落位之间留一点呼吸，而不是框和字同时砸进来。为什么不用 display 或 visibility：opacity 补间可 seek，任意时点抽帧都能还原正确的中间态；display 切换在时间轴上是硬台阶，seek 到切换点附近又会冒出不可插值的尴尬。这仍然是系列那条总原则的局部应用——**凡是要烤进片子的视觉状态，都得走 seekable 的补间**。

两处修复之后，两轮共 **47 个拍点**的 snapshot 全部目验过：每个幕的卡片位置、容器淡入时机、屏录与 freeze 的接缝、字幕压点。273 句逐句压到时间轴。check 结果 **0 error**，22 条 nested_structure 是五片基线接受项，Layout、Motion、Runtime 三阶段 0 issue，Contrast **68/68** 全过 WCAG AA——但要说清楚：两个真 bug 都不是 check 抓的。check 守规矩，「卡片此刻该不该在这」「框是不是先于内容亮相」是事实问题，照片才裁得了。

## 三、frames 与 zoom：扫雷接触表和 504 像素的高密度特写

这集分镜大量用查帧三件套自己查自己，顺手把真机画面都截成了正片素材。

frames 是整片等分扫雷：给个数，它把整片等分，开头结尾自动带上，每张按秒数命名，还送一张接触表。这集真拍的一张是五等分，时点 0、3、6、9、11.64 秒——蓝块一路从左端走到右端，红块在四个时点几乎贴着地面挪，第五格蓝块到终点、红块才跟上一点，「一个登记在时间轴、一个只认墙钟」不用旁白解释。

![frames 五等分接触表：1.0s/2.3s/3.6s/4.9s/5.11.64s 五格，蓝块沿上行从左滑到右，红块在下排起点附近缓慢挪动](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf07-review/hf07r03-contact5.jpg)

zoom 跟一个选择器，或者直接给一块像素区域，把那一块高密度裁出来。这集裁了红块本体：全屏 1920 里只有几十像素宽的运动幅度，不放大根本看不清四帧四位置。选错了它不糊弄一张全图，直接报错——这也是片里「#nope」那行红字的由来。

![zoom 选择器裁切：红「墙钟」块的高密度特写，圆角方块居中，边缘抗锯齿清晰](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf07-review/hf07r03-zoom.png)

分镜里给「拍哪些秒」定了三个必拍点，制作侧自己照做：每段 clip 接缝前后各一张（转场最易穿帮），动作半途一张（起步落位往往都对，错在半途），写得最心虚的句子点名拍。双类和空框两个 bug 都是在「动作半途」那一格现的形。

## 四、封面追改：finalize 前一刻截获的事实矛盾

第三处发生在 11:39，终片 finalize 之前（PR#185）。

这集沿用封面先行流程：立意和主视觉在开工初期就锁定（#599），v1 封面是四连拍接触表第二秒的实拍——蓝块四帧同位、红块异位——加一枚相机徽章，标题「把每一帧看清楚」。封面做得早，立意也一直没变，问题出在它**记录的事实版本是旧的**：v1 的接触表图例里，红块标注的还是「CSS 墙钟·四帧四位置」。

主角翻案发生在封面之后（#604）。红块的身份已经从「CSS 动画」改成「setInterval 闭包黑户」，绿点反倒成了合法 CSS 的证人。稿、音、分镜全跟着翻完了，封面没人回头核对——按旧流程，它会一路安静地拼进终片头两秒，和正片第 12 秒「平心而论，这事真赖不着 CSS」直接打架。观众刚看完封面被告知 CSS 是黑户，半分钟后听到 CSS 被平反，这集最值钱的翻案叙事，先被封面剧透成了自相矛盾。

拦住它的是 finalize 前的抽帧惯例：封面头拼进去之前，先把 cover-final.png 和正片关键卡并排过一眼。三处改动：

1. 红块标注从 CSS 改成 **setInterval**，与成片术语逐字一致；
2. 补上 CSS 绿点四帧同位的圆点图例——翻案后封面必须同时装得下「绿点合法、红块黑户」两件事，只剩红块单方证据反而误导；
3. 图例三项排一行，17px 字号、gap 14、`white-space: nowrap` 防折行（旧排版两行折行后第二行只剩半项，视觉权重失衡）。

重截 cover-final.png，重拼封面头。终片数据随之锁定：**561.233333 秒**（封面头精确 2.000 秒＋正片 559.233 秒），**55,869,542 字节**，h264 加 aac 双 start_time 都是 0.000000。

## 收尾：旧资产也要过事实闸

三处事故拼出一条容易漏的规矩：**翻案之后，最早交付的资产最后核对。** 封面先行本身没错——它在开工时锁住了「四连拍」这个立意，整集没有一天偏离；错的是把「立意没变」误当成「事实没变」。主角翻案改变的是接触表里每一格的身份标签，这类语义漂移不会让任何测试变红，只有把旧资产拿到新叙事旁边并排看一次才看得见。

具体动作固化为 finalize 前的三连对：封面文案与正片术语对一遍（CSS／setInterval），封面画面与最终布景对一遍（绿点要在场），封面排版在 1920 宽度下目验一遍（折行、权重、徽章对齐）。三分钟的事，挡住一次发布级矛盾。

至此所有 render 前的闸全部过完：check 0 error 是底线，47 拍点照片是事实，封面三连对是收尾。下一篇讲那 41 分钟——16777 帧怎么烤的，为什么 worker 只有一个，以及烤完之后 F2 怎么把 273 句收成 3.1 分钟的人耳合集。
