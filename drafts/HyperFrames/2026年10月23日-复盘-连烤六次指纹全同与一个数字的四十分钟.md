第一季大结局讲 render——无头 Chrome 怎样把一个网页逐格求解成 MP4。开场是 HyperFrames 最硬的一次承诺验收：一份十三秒的小工程连烤六次，六个 MP4 都是 61,145 字节、SHA256 同一个值。确定性的实验六战六胜，制作过程却在最后关头贡献了一个反例：口播、字幕、音频三层全部改对、人耳两批全过、客观比对相关系数 0.99999，一张静态卡片上的「52 秒」没人改，终片级抽帧才把它抓出来——然后整个 18,346 帧的长片重烤四十分钟。

这篇速读记录 hf-08《把网页烤成 MP4》从探针到发布的全周期：六指纹实验与两条捕获路径；worker 数是怎么算出来的；录制日连环三起事故；52→54 补丁为什么会漏掉第四层；以及「教门控的一集，自己不能绕门控」这条新纪律。细账在同组四篇深读里。

## 二、连烤六次，六个指纹同一个

render 不是「播放页面顺手录屏」。录屏是墙钟的生意，播放十三秒就得花十三秒，机器卡一下录进来的全是现场实况；render 把时间轴当数学题——每秒三十格，十三秒三百九十格，每一格都是一次独立求解：seek 到时刻，等浏览器把画面画稳，截图。求多少次答案都必须一样，墙钟被关在烤炉外面。

实验工程干净得不能再干净：黑底，五道白闪，13 秒。软件 GPU 烤两次，硬件 GPU 烤两次，单 worker 再烤一次，再翻出六天前（10-15）的旧档——六份 MP4 全是 **61,145 字节**，SHA256 全是 `2057d037…c6c5a83`，软件路和硬件路两条完全不同的捕获路径，烤出来逐字节相同。

![成片 14.5 秒：PowerShell 里 Get-FileHash 六连，六个文件同行同哈希，底部字幕「两份文件摆一块儿算指纹一模一样」](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf08-review/hf08r01-hash6.png)

这是八集一条线的闭环：第二集 init 搭骨架，第三集把网页摆上时间轴，第四集灵魂在 seek，第五集 check 把门，第六集配上声音，第七集 snapshot 验帧，第八集 render 出炉——同输入、同版本，同输出，六指纹就是第一集那句承诺的验收单。

## 三、全链五手，两条路，worker 数是算出来的

打开 `--debug`，烤一次经过五道手：compile 把工程和动画运行时打包成自足页面；无头 Chrome 先探硬件 GPU 能不能用；三百九十帧里挑五帧真截一遍测单帧成本；每个 worker 领一段帧号各开一个无头 Chrome 逐帧 seek 截图；最后三百九十张图压成无声视频再和声音合成。嵌进来的视频素材烤前按内容抽帧缓存，第二次重烤时这套缓存六段全命中，extract 阶段从 26.8 秒省到 0.1 秒。

两条捕获路径都在片里真机演示。软件路 SwiftShader 用 CPU 模拟显卡、浏览器截图命令出图，可以开三个 worker 并行，图先全部落盘、三家交活再统一编码——日志里那道 `streaming-encode gate enabled:false, reason multi_worker` 说的就是「并行截图不能边截边编」，这是门控决定的。硬件路让 Chrome 合成器用 drawElement 直接把画面交出来，这台机器上永远单 worker，边抓边编，抓完编完。

![成片 228.6 秒：软件路三 worker 并行，renderJobId 元数据里 workerCount:3、forceScreenshot:true，进度停在 25%，右侧卡片「图先全部存到盘上，等三家交活再统一编码」](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf08-review/hf08r03-sw-three-workers.png)

worker 数不是拍脑袋：CPU 核数减二、内存一半除以每 worker 1536 兆预算、总帧数除以三十、再加堆内存一笔账，四笔取最小。八核 16G 的机器算下来 CPU 给六个、内存给五个、帧数给十三个，最后被压到**三个**，和日志报的一模一样。硬件路钉死单 worker 有三层：短工程并行赚不回启动成本；超过 900 帧后实测单 worker 全程更快，多 worker 被主动反转；三硬件并发的门槛是 24G 内存——源码注释里留着事故档案，老版本在 16G 机器上开三个硬件实例，合成器瓷砖被挤掉，片子烤出竖直黑条。

## 四、录制并行口径：本集最大的实测发现

教学要的终端画面不能摆拍，全是代录脚本控制真实终端跑出来的。第一轮六 take 全错位，牵出这集制作侧最重要的发现：**gdigrab 录屏和 render 在同一台机器上抢资源，等待常量不能拿「没录屏时」的探针口径定。**

无竞争时命令行 ENTER 到 Chrome 起来只要 **8.9 秒**；录制并行时同一段横幅拉长到约 **29 秒**、到 job start 约 **37 秒**；重启后第一条冷态 render，ENTER 到 job start 实测 **66 秒**、全链 **141 秒**——而脚本最初的 WAIT 只按探针口径盖了 render 内部的 68.1 秒，后一条命令在 render 占着前台时进了输入缓冲，六条全乱。修法是完成门控 `wait_render_idle()`：node 命令行含 hyperframes 与 chrome-headless-shell 双判空、连续两轮 4 秒才放行，五个等待量按录制中真机重定（sw 155／hw 78／t3 150／t4 70.5／t5 19 秒）。

同一天还修了另两坑：`tree` 管道经 more 按 GBK 出制表字节、在 65001 代码页里解成乱码，改 `tree /F /A` 纯 ASCII；Notepad++ 非模态 Find 对话框吃键还改脏文件，改命令行 `-n10933` 直跳 17,152 物理行。第三起最险：具名单跑一段时终端窗口句柄没就位，激活静默失败、打字流向叶扬自己的窗口，异常又被 `os._exit(0)` 抢在 traceback 前面吞掉，ffmpeg 成孤儿继续写了 77.5 秒废片——修法是每段先过 HWND 窗口闸、完整栈先打印再退出、异常时 taskkill /T 连 ffmpeg 一起收。

## 五、52→54：一个数字，四层补丁，四十分钟重烤

全片最戏剧性的事故出在封板之后。事实背景是双口径：探针日没有录屏竞争，硬件路小工程实测 **52.4 秒**；录制日同机 gdigrab 抢资源，入镜母带尾报 **54.2 秒**（totalElapsedMs 54145：setup 9.4／capture 41.1／assemble 1.9）。观众看到的数字要以入镜口径为准，口播原词「硬件路五十二秒」必须改。

补丁按熟路做了三层：src 改词，蝉镜试听通道 0 蝉豆重取整句「硬件路五十四秒，编码和抓帧重叠在一起」（4.045 秒），20 毫秒 RMS 包络谷底定窗 267.24–271.12 秒、atempo 1.0425、两端 12 毫秒余弦淡化替换；cues 字级加组句回填；F2 人耳 38 点合集 2.7 分钟两批听完，原话「全部没问题，继续」。中间还揪出补丁工艺自身的隐患：首版替换窗被同窗 whisper 转写听成「抓抓珍珠直接在一起」——hf-05 传下来的旧算法只淡两端，窗中段是原音与补丁两路念白全程叠加，hf-05 靠 0.9949 的近速率蒙混过耳，1.0425 失步立刻露馅，改成中段清零的真交叉淡化才对。

8:26 第一版 render 跑完（43 分 04 秒、67,058,608 字节），finalize 出第一版终片，客观验收硬得不能再硬：补丁窗从终片 body 抽 PCM 对 patched 母带，180,480 样本相关系数 **r=0.99999**，视觉十关键位接触表也过了。但补抽的 270 秒全尺寸帧上，m10 时间账卡第三行赫然还是「硬件路 **52** 秒」——同一帧底部字幕已是「五十四秒」。补丁只改了 src／cues／音频三层，静态分镜卡（make_video.py 里的 tr-3）漏改；同卡「56 秒以内」还因 220px 列宽折成两行。听感三层全过，不代表画面过。修复两行：52→54，列宽 220→260 像素。9:29 重烤：capture **38 分 15.6 秒**、全程 **40 分 15.1 秒**（2,415,119 毫秒），产物 67,057,066 字节，18,346 帧，0 error。

## 六、教门控的一集，自己不能绕门控

这集教学内容的另一半是失败学。lint 默认只警告不拦截：红方块用 requestAnimationFrame 自己掐墙钟表跑，lint 报两个 error，render 照样出片，墙钟动画真真切切烤进 MP4——加 `--strict` 才在 error 处中止，一片不出；但音频文件不存在属于正确性问题，默认模式也直接 exit 1，画面烤完临合成拦下；页面既没注册时间轴又忘了 `data-no-timeline` 标记，机器死等 **45 秒**才放弃。崩了有三件套：`--debug` 保第一现场、worker 静默退出八成是内存（`-w 1` 隔离重烤）、分段捕获支持断点续烤；三道超时分别是开页面 60 秒、协议通话 300 秒、等就绪 45 秒。

![成片 436.9 秒：--strict 模式终端 Aborting render due to lint issues，右侧卡片「想让它拦，加 --strict」](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf08-review/hf08r06-strict-abort.png)

![成片 455 秒：缺音轨工程终局，Render blocked: audio_processing_failed，输出会变成哑巴片，exit 1](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf08-review/hf08r07-missing-audio.png)

耐人寻味的是制作侧一个反向决定：热态演录那天把早前留下的「素材文件不存在就降级跳过」机制**主动移除**了——缺资产应该让 check 直接报 missing_local_asset，教门控的一集自己不能留一扇绕门控的后门。冷态 68.1 秒在开机 26 小时后不可复现，叶扬的选择也是不造假：热态演录、切点避开尾报，文案锚定探针台账的历史数字（68.1）并加注记，绝不为了入镜去凑一个冷态读数。

## 七、这集新长出来的规矩

1. **事实数字的句级补丁必须四层同改：src、cues、音频、静态画面卡。** 听感三层全过不代表画面过；补丁句出现时刻 ±3 秒的终片级抽帧接触表是最后一道闸。40 分钟重烤反证补丁当时就该 grep 全部视觉物。
2. **等待常量必须在「录制中」实测。** gdigrab 同机抢资源使 CLI 与 setup 前置翻倍（8.9 秒对 29/37 秒），探针无竞争口径系统性偏短；会话首条 render 一律按冷态定时长，跳过冷态必须先暖场。
3. **句级音频补丁必须真交叉淡化。** 只淡两端、中段两路叠加，速率差超过 4% 必露马脚；同窗 whisper 三版对照（补丁窗／原母带同窗／补丁原始句）是客观验收法。
4. **冷态不可复现时不凑数。** 代录重演加历史探针台账锚数字、尾报避开，比重启摆拍合规。
5. **门控主题的片子自己不绕门控。** 文件存在性降级在素材归位后即移除；缺资产让检查器直接报错。
6. **cues 字级回填必须连字一起改。** 只改句的 s/e 时间点，文本仍旧。

下一季片子离开本机：cloud、lambda、cloud run，把烤炉搬进机房，多台机器一起烤，benchmark 帮着挑配置。片尾三枚按钮亮起来的时候，10 分 13 秒的季终片烤完，第一季也烤完了。
