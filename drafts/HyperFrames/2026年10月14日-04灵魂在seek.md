上一集，叶扬做出了第一个真正属于自己的 clip：标题第二秒进来，第六秒走。可打开浏览器盯着看——它不是「进来」的，是「砰」的一下，杵在那儿的。静态页面嘛，只会出现和消失，不会动。

这一集，让它飞进来。这也是整个 HyperFrames 系列最核心的一集：在 HyperFrames 里写动画，跟在普通网页里写动画，规矩不一样。不一样不在语法，在这东西的**播放方式**。

## 一、渲染器不是摄像机，是随机点名的提问者

先搞清楚一条 30 帧每秒的视频是怎么出帧的。

普通人的想象是：渲染器把网页从头播一遍，旁边架台摄像机录屏。不是。渲染器干的事是反过来的——要第几帧，就算出这一帧对应的秒数 t，然后问页面：**把你拨到 t，你长什么样？** 页面摆好，截图，下一帧。

关键细节有两个：

- 它不等页面。不是从第 0 秒陪你跑到第 7 秒，而是这一帧问第 2 秒、下一帧可能直接问第 7 秒，要帧的顺序是随机的；
- 正式 render 时，多个无头 Chrome 并行干活，大家抢 CPU，谁快谁先交卷。

![深色概念卡：给你任意一个秒数 t，你能不能立刻摆出那个瞬间的样子？大字 seekable，可定位](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04/hf04-01-seekable.png)

*每一样会动的东西，都得回答同一个问题：任意一秒，你长什么样？*

所以页面上每一样会动的东西，都得回答同一个问题：给你任意一个秒数，你能不能**立刻**摆出那个瞬间的样子？不用等，也不依赖之前发生过什么。这个特性英文叫 seekable——可定位。

程序员可以这样理解：每一帧都得是时间的纯函数，`frame(t)`，同一份输入必出同一份画面。正因为如此，渲染才能并行、才能缓存、才能重试；也正因为如此，这类工具才敢说自己「为 agent 而生」——AI 把页面改十遍，第 137 帧该是什么样，板上钉钉，不看心情。

## 二、CSS 动画实测：居然能定位？

按老习惯，让一个块飞入，写个 `@keyframes` 就够了：起手透明、往下挪 60 像素，0.8 秒归位。回浏览器点播放，标题确实飞进来了，挺正常。

但「播放正常」不算数，seekable 不 seekable，截帧看。用 snapshot 分别截第 2.1、2.5、2.9 秒三张：

![黑底白字「我的第一个片段」半透明停在半路，底注：2.5s 半透明，停在半路](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04/hf04-02-css3.png)

*第 2.5 秒：淡淡的影子停在半路，正是动画该有的中间态*

结果三张全对：2.1 秒淡影刚冒头，2.5 秒半透明停半路，2.9 秒白了、归位。叶扬不放心，同样三个时刻再截一轮——同一时刻的两张图，逐字节一模一样，一个像素都不带差的。

谜底是运行时偷偷替你接管了 CSS 动画的时钟。普通网页里，动画一加载就自顾自播，它的时钟是墙钟；HyperFrames 运行时把这个播放头摘下来，绑到了**片段自己的时间轴**上——标题第 2 秒进场，动画就从第 2 秒开始算。每次截帧前，运行时先替你把动画拨到该到的位置。所以帧帧都对。

听到这儿是不是觉得「那还学什么，CSS 全搞定了」？别急。

## 三、setInterval 实测翻车：排队两种，并发三种

叶扬在页面上加了个计数器：最普通的 `setInterval`，每半秒数字加一。浏览器里看，数字跳得欢，一点毛病没有。

还是不猜，分两轮验。第一轮排队：同一个第 2 秒，连截三张。

![三个深色窗口并排：ser-1 tick 3、ser-2 tick 3、ser-3 tick 4（独一份）](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04/hf04-03-tickqueue.png)

*排队问同一个第 2 秒，答案都不唯一：两张 tick 3，一张 tick 4*

两张 tick 3，一张 tick 4——连排队都给不出唯一答案。道理很简单：截一帧得现起一个浏览器进程，从页面打开到按下快门，墙上的钟实打实走过一两秒；计数器半秒跳一下，这趟启动快是 tick 3，下趟启动慢了零点几秒，回来就成了 tick 4。

机器闲着都只差这一下。正式出片比这狠得多——叶扬写了个小脚本，喊 6 个渲染器同时开工，全问第 2 秒，谁也不许等谁：

![六个窗口两行排列：tk-1 tick6、tk-2 tick6、tk-3 tick7、tk-4 tick4（独一份）、tk-5 tick6、tk-6 tick7](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04/hf04-04-sixrace.png)

*一窝蜂问同一个第 2 秒，出了三种答案；被挤最狠的一路计数器跳得最少，抢不到 CPU 反而冻在 tick 4*

六张图回来，tick 4、tick 6、tick 7，整整三种。终端自己给结论做了总结：排队问，两种；一窝蜂，三种。因为 render 默认就是多个无头 Chrome 并行、随机跳帧要画面——跟脚本里是同一个场面。

为什么 CSS 动画行、定时器不行？因为 `setInterval` 只认墙钟：页面打开后真实过了几秒，它就跳几下。渲染器问它「第 2 秒你长什么样」，它答不上来，只会说「我**现在**是什么样」；而这个「现在」，取决于那个进程这会儿抢不抢得到 CPU。

规矩由此成立：凡是跟着真实时间自己往前跑的东西——`setInterval`、`setTimeout`、在 `requestAnimationFrame` 里手改样式——在视频里都是薛定谔的画面。动画的时间，必须交给一根能来回拨的轴。

## 四、check 全绿，也救不了你

这一课还有个扎心的地方：上面那个不可定位的计数器页面，`check` 跑出来是全绿的，零错误。

守门员能查布局、查越界、查对比度，但查不出「你这段动画在并行渲染时给不出确定答案」——结构合法、对比度达标、运行时无报错，它没有理由拦。seekable 是设计层面的约定，不是 lint 规则，这一课只能自己懂。

## 五、正道：GSAP 三件事

官方样板替你接好的正道，是 GSAP 的时间轴。页面骨架底部早就留好了位置，一共三件事。

**第一件：建轴的时候让它生下来就暂停。**

![Notepad++ 中第 39 行 const tl = gsap.timeline({ paused: true }) 高亮](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04/hf04-05-paused.png)

*`paused: true`——这条轴一秒钟都不自己走*

```js
const tl = gsap.timeline({ paused: true });
```

这条轴一秒钟都不自己走。它更像一个函数：喂它一个时间 t，它还你那个瞬间每个元素该有的样子，而不是一段自顾自播放的动画。

**第二件：动画照写，但往轴上挂，而且带时刻。**

![Notepad++ 中三行 tl.fromTo：标题挂第 2 秒、卡片挂第 3 秒、副标题挂第 6 秒](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04/hf04-06-fromto.png)

*每个 `fromTo` 最后一个参数就是挂在轴上的位置：2、3、6*

```js
tl.fromTo("#title", { opacity: 0, y: 60 },
          { opacity: 1, y: 0, duration: 1.4, ease: "power2.out" }, 2);
```

标题第 2 秒进场，动画就挂在 2 的位置；卡片挂 3，副标题挂 6。暂停着没关系，轴全记得住。

**第三件，最容易忘：注册。**

![Notepad++ 中第 42 行 window.__timelines["main"] = tl 与 data-composition-id="main"](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04/hf04-07-register.png)

*报到行：轴注册到表上，名字 main 跟 #root 身上的 data-composition-id 对得上*

```js
window.__timelines["main"] = tl;
```

main 是谁？回头看 `#root` 身上的 `data-composition-id="main"`。这行是报到：渲染器渲染 main 的时候，按名字来这张表取轴。底下还留着一行 `tl.seek(0)`，页面一摆好先定位到第 0 秒，省得开头闪一下终态。

有人会发现：不注册、直接写全局 GSAP 动画，眼下这个版本好像也能播、截帧也对。没错，运行时会好心帮你代理简单的全局动画——但那是它「猜中了」，不是「保证了」。一条轴上挂几十个动画、有相对位置、有嵌套、有瞬间跳变，代理猜不过来。写能被保证的代码，别写指望别人聪明的代码。

## 六、亲手拨：window.__player 和「轴不管出场」

光说不练不过瘾，打开开发者工具，在控制台亲手拨。

页面上有个现成的播放器对象，seek 方法就在它身上：

![Edge DevTools 控制台执行 window.__player.seek(6.3)，画面中标题就位、卡片与副标题停在半路](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04/hf04-08-devtools.png)

*`seek(6.3)`：副标题浮在半路。连着五回 seek 同一个 2.4，五回画面一模一样*

喂 2.4，画面「啪」回到半透明浮在半路；seek 3，标题就位；seek 6.3，副标题在半路；seek 9，全在；seek 0，空舞台。连拨五回同一个 2.4，五回画面一模一样。时间在这儿能倒着拨、来回拨。

一个自然的疑问：刚注册到 `window.__timelines` 上的那条轴，直接调它的 seek 不行吗？还真不行——**轴管的是动画值，片段第几秒露面、第几秒退场，是播放器管的**。直接拨轴，数值拨回去了，人还藏着：第 9 秒标题透明度是 1，画面上却没有它。想亲手拨，找 `window.__player`，它一声令下，轴和片段一起就位。这是两层职责，别混。

顺手再记一条踩出来的坑：交给时间轴的动画，只让它一个人管。位移、缩放、透明度走 transform 和 opacity 没问题，但别手贱，再给同一个元素写一条 CSS transition——两个管家抢一个属性，渲染器瞬间设值、transition 想从头补间，同一秒截两回可能就是两张脸。**一个属性，一个管家。**

## 七、渲染揭底：GSAP 只是一种适配器

窗户纸到此可以捅破了。render 出片时，无头 Chrome 干的事跟你在控制台里干的一模一样：帧号除以帧率算出 t，调一声 seek，时间轴把所有元素瞬间摆到位，浏览器算完样式，截图。10 秒的片子 300 帧，就实打实干 300 次 seek 加 300 张截图——叶扬这台机器跑了 39 秒——最后交给 FFmpeg 烤成 MP4。你在控制台手拨，等于人肉当了一回渲染器。

也正因为如此，GSAP 不是唯一选择：

![六枚标签：CSS 动画、WAAPI、Lottie、Three.js、Anime.js、自研对象，汇入中央 seek(t) 契约卡](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04/hf04-09-adapters.png)

*渲染器不在乎你轴里存的是什么，只认一个约定：我喊 seek(t)，你让画面立刻就位*

CSS 动画和浏览器原生 WAAPI，运行时自动接管，等于内置了适配器；Lottie、Three.js、Anime.js 各有各的时间轴对象，可以挂到这张表上；乃至你自己写一个对象，里头实现一个 `seek(t)` 方法，也行。渲染器不在乎你轴里存的是什么，它只认一个约定：**我喊 seek(t)，你得让画面立刻就位**。适配器模式，老程序员一看就懂。

## 八、回去查三条

![三条行动件：时间交给能来回拨的轴；GSAP 轴 paused=true；注册到 window.__timelines 且名字对得上](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04/hf04-10-action3.png)

*这集的完工验收清单，回去对着自己的 index.html 逐条查*

1. 动画的时间，是不是交给了一根能来回拨的轴，而不是跟着墙钟自己跑；
2. GSAP 时间轴是不是 `paused: true`，每个动画都带时刻挂在轴上；
3. 有没有注册到 `window.__timelines`，名字跟 `data-composition-id` 对得上。

三条齐，动画才是能被渲染的动画。
