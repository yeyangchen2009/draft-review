速读里讲了全周期，这一篇只讲 hf-08 的开场实验：同一份工程连烤六次，六个 MP4 的 SHA256 为什么能一模一样；以及这件事成立的边界在哪里。素材全部来自开拍前一天（2026-10-21）叶扬在 0.8.107 上跑的真机探针台账，命令实跑、数字附日志，布景冻结后录屏组原样重演。

## 渲染这两个字的坏名声

做视频的人对「渲染」天然不信任。同一份工程，今天烤和明天烤、这台机器和那台机器，常常给你不一样的结果：字体回退变了、解码器小版本变了、编码器往容器里写了当前时间、并行任务抢 CPU 导致浮点求和顺序变了……任何一处带进来随机量，产物的指纹就不同。

所以 hf-08 开场不先讲命令，先做实验。工程是仓库内的标定片 av-sync-calib：13 秒、390 帧、纯黑底上五道白闪，简单到没有地方可以藏随机性。同一条 render 命令，只改输出名，连跑六次，条件分别是：

| 跑 | 条件 | 墙钟 | SHA256 前 8 位 |
|---|---|---|---|
| 2026-10-15 旧档 | 六天前的历史产物 | — | 2057d037 |
| run-a | 软件 GPU，3 worker | 1 分 8.1 秒 | 2057d037 |
| run-b | 同上当轮热跑 | 55.7 秒 | 2057d037 |
| w1 | 软件 GPU，单 worker | 50.7 秒 | 2057d037 |
| hw-a | 硬件 GPU，drawElement | 52.4 秒 | 2057d037 |
| hw-b | 同上再跑一次 | 54.1 秒 | 2057d037 |

六份文件全是 **61,145 字节**，完整指纹 `2057d037…c6c5a83`。最狠的是软件路与硬件路——SwiftShader 用 CPU 模拟显卡、走浏览器截图命令，硬件路让 Chrome 合成器用 drawElement 直接交画面，两条完全不同的像素生产路径，产物逐字节相同。

表里还有一个容易被忽略的数：w1 软件单 worker 跑了 50.7 秒，比硬件路两次都快。不矛盾——单 worker 时流式编码门是开的（日志里 `enabled:true, reason:"single_worker"`，另有 240 秒时长闸），软件路也能边抓边编；而这份工程只有 390 帧，硬件路在 GPU 探测和合成器通路上的启动开销摊不回来。路径没有绝对的快慢，只有帧规模上的算账，这套账深读之四展开。

![成片 14.5 秒：PowerShell Get-FileHash 六连，soft-a/soft-b/hw-a/hw-b/w1/1015-old 六行同一个哈希](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf08-review/hf08r01-hash6.png)

## 不只是文件级：三层校验

叶扬没有只算一个整文件哈希就收工，探针台账里记了三层：

1. **整文件 SHA256**：`2057d037…c6c5a83`，容器层不写可变时间戳，六个文件全等；
2. **视频压缩流 md5**（`ffmpeg -c copy -f md5`，不重新编码）：`b55c5ad2…`，全等——说明差异没有藏在容器封装里；
3. **解码到像素**：yuv420p rawvideo 的 md5 `fb0c5653…`，全等——连最终像素数组都一样；音频流 md5 `42de6ec9…` 同样全等。

白闪时刻还做了像素抽查：第 89 帧 mean=0（全黑），第 90/91/92 帧 mean=255（全白，对应 t=3.000–3.066 秒的三帧白闪），第 93 帧归 0。指纹相同不是「黑帧碰巧一样」，白的地方确实白过。

台账里还留了一条反直觉的提醒：这份工程的黑帧和白闪帧压成 JPG 后都是 12,998 字节。**不能拿文件大小判断帧内容**，要判就得看像素。这条后来在彩排像素闸里一直受用。

## render 为什么能确定：逐格求解

指纹相同的根因是 render 的工作方式。录屏是墙钟的生意：播放一遍 13 秒就得花 13 秒，机器卡一下、后台忙一下，录进来的全是现场实况。render 不认墙钟，它把时间轴当一道数学题：

- 每秒三十格，13 秒＝390 格，每一格里只问一个问题：「第 N 帧应该长什么样？」
- 把时间轴 **seek** 到这个时刻，等浏览器把画面彻底画稳，再截一张图；
- 第一格、第一百格、第三百九十格，谁先求谁后求无所谓，求多少次答案都必须一样；
- 390 张静态图交给编码器压成无声视频，声音走另一条路单独处理、按时长归一，最后两路合成一个 MP4。

每一帧的画面只由时间码唯一决定，墙钟被彻底关在烤炉外面。这正是 hf-04《灵魂在 seek》那一集埋的线：登记在时间轴上的动画（GSAP、CSS/WAAPI）可以被 seek 到任意时刻；hf-07 又证明了闭包里自己掐表的 setInterval 是 seek 管不着的黑户。到了 hf-08，seek 不只是播放器的功能，它就是生产方式本身。

## 确定性的边界：哪些话不能说

探针台账里专门有一节「口径注意」，这是叶扬写稿时给自己画的线：

- 实验工程内容极简（纯黑加白闪），证明的是**同一条渲染路径上，帧位置由 seek 时间码唯一决定、编码与 mux 不带入随机量**；
- 复杂工程（字体、CSS 渐变、阴影）跨软件/硬件路径的像素级一致性，这次**没有做全样本比对**，所以口播不断言「任意工程软/硬件烤出来逐字节相同」，只断言「同参数重跑逐字节相同」；
- 绑定条件写明：**同输入素材＋同 CLI 版本**。这就是全季钉死 0.8.107、不追 latest（当时已是 0.8.181）的原因——官方从不承诺像素跨版本一致，render 结尾那行版本过期提示一季看了八次，一次没升。

确定性是函数意义上的：同输入、同版本，同输出。多一个条件都不白送。

还有一层要说清：确定的是**产物**，不是墙钟。六跑的耗时分别是 68.1、55.7、50.7、52.4、54.1 秒，冷热不同、路径不同，没有任何两次一样；但每一次的输出文件比特相同。render 把「答案」和「求出答案花多久」切成了两件互不相关的事——这正是逐格求解模型的性质：第 N 帧是一个纯函数，求值耗时是运行时的偶然。后面所有时间账都要带口径读，根也在这里。

绑定条件也在工程上兑现：全季钉死 0.8.107 不追新版，源视频抽帧用按内容寻址的缓存（同一份素材任何工程里都只抽一次），render 自己的 summary 里还有 compositionHash 内容指纹——第二次重烤时 compositionHash a527b033 与缓存键一对上，六段素材直接免抽。版本和输入都被管住，指纹才敢当验收单。

## --debug：把烤炉拆开给人看

这个实验任何观众都能在自己机器上复现，命令面零门槛：烤两遍（软件路 `--no-browser-gpu`、硬件路 `--browser-gpu`，再加 `-w 1` 单 worker），然后在 PowerShell 里一句 `Get-FileHash *.mp4 -Algorithm SHA256 | Format-Table`——片里 14.5 秒的终端画面就是这条命令的真机输出，六个哈希排成一列。这也是片尾行动件的来历：别信承诺，自己烤一遍，自己算一次指纹。

六指纹回答「相不相同」，`--debug` 回答「怎么烤出来的」。这个开关让中间产物一件不扔，全部落在 npx 包目录的 `.debug/<jobId>/` 下，叶扬把整个目录摊开核对过一遍：

```
compiled/index.html + summary.json   编译后工程＋媒体清单（尺寸/时长/视频音频轨）
capture-calibration/                 校准会话：真开一次浏览器，采第 0/97/195/292/389 五帧量 p95 耗时
capture-attempt-0/worker-0…2/        每 worker 一个 Chrome，各领一段帧号
captured-frames/frame_000000.jpg…    汇合后 390 张 JPG（6 位编号，0 起）
audio.m4a / audio.duration-normalized.m4a   音频处理＋时长归一
video-only.mp4                       390 JPG → 无声 H.264（37,157 字节）
output.mp4                           视频＋音频合成（61,145 字节，与正式产物同哈希）
perf-summary.json + render.log       阶段账本与全量 trace
```

想看得更原始，可以用 `--format png-sequence` 让流水线停在「390 张 PNG 加一条声音」那一步——3.2MB 一个目录，不封视频流，encode 只花 0.4 秒。烤炉的原始产品就摊在眼前：不是视频，是一沓照片。这也是片里行动件的来源：每个观众都可以自己烤一遍、再烤一遍，算一次指纹。

![成片 248.2 秒：硬件路 capture_streaming 实时日志，38%→52%→66% 进度与 Streaming frame 逐帧 trace，右侧卡片「边抓边编码，抓完也编完了」](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf08-review/hf08r05-hw-streaming.png)

流水线五道手由此钉死：compile 编译打包 → 无头 Chrome 硬件 probe → 五帧 calibration 测这台机器上单帧成本 → worker 分段 seek 截图 → 编码合成；工程里嵌了视频素材的，烤前多一道按内容寻址的抽帧缓存——第二次重烤时六段素材缓存全命中，extract 从 26.8 秒掉到 0.1 秒，这套缓存的账在深读之四里细算。

目录里还有两处细节值得多看一眼。一是每 worker 每次导航都要走一遍固定的就绪序列 initSession：page.goto 之后先给 GSAP proxy flush，再 pollHfReady、pollSubCompositionTimelines，然后 applyVideoMetadataHints，等媒体、字体、tailwind 全部 ready，最后才做 static-frame 静帧判定——「画稳」两个字不是一句口号，是一整串可以轮询的状态。二是静帧去重：相邻画面完全相同的帧不必重复截，早期梁武片工程里 3682 帧复用了 57 帧；av-sync 这种没有 GSAP tween 的工程该机制直接 disabled，三百九十格一格不省。音频也有自己的工艺：audio.m4a 旁边会多出一个 audio.duration-normalized.m4a，声音按时长归一后再合成，时长不被音频编码的小误差带跑。

顺带记一条文案滞后的实测：帮助文本说 fast capture（边抓边编的流式捕获）只在 macOS 加硬件 GPU 时才能 engage，真机上 Windows＋UHD 620＋152 版 Chrome 已经 engage，capture 40.5 秒与 encode(during capture) 40.5 秒完全重叠就是证据；遇到不兼容构图或自校验失败，它还会自动回退到 screenshot 路径。文档说不算，真机日志算。

命令面探针还摸清了一些用不上但要知道边界的参数：画质 draft/looks/delivery 三等（默认 looks 对应 CRF16），格式 mp4/webm/mov/gif/png-sequence/hls 六种；`--frames-cache-dir` 能把源视频的抽帧缓存挪出系统盘（这台机器 C 盘紧张，后来长片都重定向）；`--variables-file` 加 `--batch` 可以变量化矩阵出片；fps 除了 30 还支持 30000/1001。这些只在台账里挂号，片子一个都没演——教学口径始终贴着实际用的命令走。

六指纹是第一集那句「同输入、同版本，同输出」的验收单，也是后面所有工艺的地基：正因为重跑确定，探针台账的数字才敢当历史锚点引用，断点续烤、分段捕获才成立，一万八千帧的长片才敢在改了两行卡片之后放心重烤——烤出来的每一帧，除了被改的那两格，都和上一次一模一样。

下一篇讲这集制作侧最大的发现：录屏和 render 在同一台机器上抢资源时，所有等待时间都得重新量——以及连着发生的三起录制事故。
