> 之一：五个小时录九分半——深夜代录的四个实拍坑
> 之二：33 路抽帧崩了一半——VFR 病根与 CFR 根治

> 之四（本篇）：一块不存在的浮层——57 点验收与 ROI 取证

终片到手不等于完工。hf-04 的终片进了第二轮复查，内部叫 F2：57 个抽帧点，逐帧目验。

56 个点过了。卡在 296 秒附近的，是一个看起来确凿无疑的穿帮——NPP 代码区上浮着一层深色的东西，像个没藏干净的浮层。

最后查证的结果是：**浮层不存在。** 但它不存在的证明过程，比发现它更值得写。这一篇讲 F2 的 57 个点是怎么设的、精确抽帧踩的 sparse-keyframe 坑、以及怎么用 300 个亮度采样点把「眼睛看到的异常」变成「像素给出的判决」。

## F2：57 个点的验收契约

先讲 F2 本身。一轮复查（F1）是跟着分镜走的粗验，F2 是终片维度的细验，57 个点不是均匀撒胡椒面，是按一套层级选的：

![F2 57 点拼版](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04-deep/hf04d10-f2sheet.png)

- **封面两点**（0.5s、1.9s）：验封面静帧的入场与保持；
- **正文入点**（body-in，2.1s）：封面 2 秒让出后第一帧必须就是正文，黑场或残留都算事故；
- **26 幕的幕中点**：每一幕取时间轴正中那一帧，幕中是字幕、画面、概念卡三者同时稳定的时刻，最能代表「这一幕长什么样」；
- **所有接缝与切点**：fade in/out、freeze 切入切出、录屏段与合成段的交界，两侧各取一点。

抽出来的帧拼成三张 contact sheet（上图是第一张，A0 到 S20 共 21 点），帧上带黄色时刻标签和当时字幕，一眼能扫完整片骨架。单帧同时存成 00–56.png 供放大看细节。

补一句 F1 和 F2 的分工。F1 在分镜阶段做，看的是「每一幕自己对不对」：布景、字幕、动画方向，跟着单幕走；F2 在终片上做，看的是「拼起来之后还对不对」，重点天然偏向接缝——封面让位、fade 起止、freeze 切点、录屏段与合成段交界。单幕都对不等于拼起来对，而且 finalize 会把 2 秒封面头拼到最前，正文时刻整体平移，F1 验过的时刻到 F2 全部要换算：**终片 T≥2 才是正文，对应正文时刻 T−2**。

幕中取点也是稳定性几何决定的：幕的边界是动画进出的高发区，半透明中间帧密集，幕中才是字幕、卡片、底注全部到位后的稳态；在稳态帧上发现的异常，最不可能是动画中间态的误读。说句事后话，这次唯一的疑点恰恰出在非稳态的淡出中段——稳态巡逻没抓到的东西，是被接缝点（freeze 切点两侧）抓到的，这也反过来证明四类点缺一不可。

这套设计的核心是把「看一遍片子」换成「**验一份清单**」。连续播放时人眼是被叙事牵着走的，浮层闪 0.35 秒你只会觉得「刚才好像有点什么」；清单模式下每一帧是独立受审的，异常无处借力。57 这个数字以后还会涨，但层级结构不变：封面、入点、幕中、接缝——四类位置覆盖了时间轴上所有「容易出事且出事观众必看见」的地方。

## 疑点：296.10，深色浮层压在代码区上

疑点帧出现在 seg6 的 GSAP 段，终片约 296.10 秒：NPP 代码页上，一层深色矩形半透明地压在第 12–15 行浅绿代码区上，矩形里还能看到 `const tl = gsap.timeline({ paused: true })` 的字样。

看到这一帧时，嫌疑人名单立刻排了出来，全是老熟人：

1. **浏览器扩展注入**——之一里沉浸式翻译红钮的同伙，又一个 Shadow DOM 客人；
2. **录屏穿帮**——第二扇窗、工具提示、右键菜单残帧；
3. **概念卡渲染残留**——上一张卡没退干净，和代码页叠在同一帧；
4. **合成轨道 bug**——字幕轨或卡片轨的 z-index 错乱。

四类嫌疑人对应四种修法，而且有两种（扩展、穿帮）意味着要回炉素材。不能凭感觉断案。叶扬做的第一件事，是把这一帧周围的时间轴精确抽出来看。

然后就踩进了一个完全不相干的坑。

## 抽帧坑：`-ss` 放前面，296 秒退化成 22.5 秒

第一版抽帧命令顺手写的是 input seeking——`-ss` 放在 `-i` 前面：

```bash
ffmpeg -ss 296.10 -i final.mp4 -frames:v 1 out.png
```

抽出来的帧一看，时间码对不上，画面是片头 22.5 秒的内容。连抽几个时刻，落点全部错乱。

原因：终片是 **sparse-keyframe** 文件。之二里讲过精切录屏段加了 `-g 30`，但终片是 assemble 阶段重新烤出来的，关键帧间隔由终片编码器决定，仍然稀疏——两个关键帧之间可以隔几十秒。input seeking 的语义是「先跳到最近的关键帧，再从那里开始解码输出」，它快，但在稀疏关键帧文件上，296.10 秒这个请求被退回到了它之前最近的关键帧，那是 22.5 秒。

![input seeking 与 output seeking](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04-deep/hf04d11-seekmap.png)

正确写法是 **output seeking**——`-ss` 放到 `-i` 后面：

```bash
ffmpeg -i final.mp4 -ss 296.10 -frames:v 1 out.png
```

语义变成「从头逐帧解码，解到 296.10 秒再输出」，落点精确到帧。代价是慢：606 秒的片子，深位置抽一帧要 30–50 秒，因为前面 296 秒一帧不少都得解。批量循环抽帧时还有第二个坑：**必须加 `-nostdin`**。ffmpeg 默认挂着一个交互解析器，循环里它会把脚本喂给后续命令的 stdin 吞掉，报一堆 `Enter command`、`Invalid duration` 的鬼错，单条命令跑永远复现不了。加上 `-nostdin` 显式关掉交互，批处理才正常。

工具坑清完，296 秒前后的帧序列终于精确到手。画面讲的故事是：深色矩形从 296.00 秒开始变淡，0.35 秒后完全消失，底下浅绿代码区完整露出来，296.20 秒画面切到同源 freeze 帧。

「浮层」在消失，不是在出现。但这还不够定性——淡出的东西也可能是穿帮物。需要判决。

## ROI 取证：让 300 个亮度采样点说话

肉眼能做的事到此为止了。叶扬需要回答的问题是：**这 0.35 秒的变化，是不是工程里某一条已知动画指令的精确执行？** 如果是，它是设计；如果曲线形状对不上任何指令，它是事故。

做法是 signalstats 像素取证。在画面上选一个小区域（ROI）：`crop=1000:130:280:185`——从 (280,185) 起、1000×130 的一条，恰好是 NPP 第 2–4 行浅绿代码区，深色卡片离开时，这片区域会被完整「揭开」，亮度变化最纯，没有字幕和别的元素干扰。然后让 ffmpeg 逐帧算这个区域的平均亮度：

```bash
ffmpeg -i gsap-paused.mp4 -vf "crop=1000:130:280:185,signalstats,metadata=print" -f null -
```

两个工具细节值得记：`metadata=print` 的输出是 **info 级**日志，习惯性加的 `-loglevel error` 会把结果连澡带孩子一起倒掉，必须让日志停在 info；300 个采样点（约 10 秒 × 30fps）的 YAVG 读数落出来画成曲线。

![ROI 亮度曲线](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04-review/hf04r03-roi.png)

曲线讲了一个干干净净的故事：

- **296.00 秒之前，YAVG ≈ 47 的长平台**（实测最小 46.9986）。深色的 `#g1-card` 不透明地盖在这片浅绿代码区上，盖住的区域平均亮度就该是这个数；
- **296.00–296.35，亮度单调爬升，宽度恰好 0.35 秒**；
- **296.35 之后，YAVG ≈ 192 的长平台**（最大 192.614）——浅绿代码区自己的底色，卡片完全离场；
- **296.20 秒那条绿色虚线是 freeze 切点，接缝两侧读数同为 192，零跳变**——freeze 帧和它前一帧在这片 ROI 里逐像素连续，切点不可见，这顺带验了之三讲的 freeze 工艺。

判决的关键证据，是那个 **0.35 秒**。工程源码里这一段的 GSAP 指令写着：

```js
tl.to('#g1-card', { opacity: 0, duration: .35 }, 296.0)
```

时间轴 296.0 秒，卡片透明度归零，时长 0.35 秒。像素曲线的爬升起点是 296.00，宽度是 0.35 秒，**逐帧对得上，连一个采样点的偏差都没有**。世界上没有哪个浏览器扩展或穿帮窗口，会按照工程源码里 GSAP 指令的起始时刻和 duration 来改变透明度——能做到这个精度的，只有指令本身。

![浮层帧与离场帧对照](https://raw.githubusercontent.com/yeyangchen2009/draft-review/main/assets/hf04-review/hf04r04-fadecard.png)

所谓浮层，是 `#g1-card` 这块**自家代码卡**淡出开始后 0.1 秒的中间帧：半透明的深色卡片压在浅绿代码上，透明度恰好在半途，肉眼就把「卡片在离开」读成了「有东西浮上来」——连运动方向都看反了。右边 296.50 秒是 freeze 切点之后，卡片早已离场，画面连续。设计行为，不是缺陷。

57 个点全部结案。

## 为什么值得为「看错一眼」查这么深

事后回头看，这一帧就算误判，最坏后果是什么？是叶扬把一段精心设计的淡出当成 bug 删掉或重做。代价不算天塌。但这套动作的价值不在这一帧：

**第一，F2 的契约是「可复查、可定位、可判决」。** 57 点清单让异常能定位到 0.1 秒；ROI 曲线让判决不依赖人的心情。下次再遇到疑点，流程不用重新发明——选区域、采曲线、对指令，半小时结案。

**第二，肉眼负责报案，像素负责判案，两者不能互相替代。** 连续播放时那「一闪」是宝贵线索，没有它根本不会有这场调查；但「看起来像浮层」永远不能当证据——人眼对透明度动画的方向判断本来就不可靠，半透明覆盖和半透明浮入在视网膜上是同一堆像素。300 个 YAVG 数字没有立场。

**第三，取证设计要有「假如真出事会看到什么」的反证。** 选 ROI 时就想好了：如果浮层是真的，曲线上会出现和任何指令时长都对不上的台阶，或者在 47 平台之外多出一段平台；如果是穿帮窗口，亮度不会是单调爬升，边缘区域会有同步突变。曲线把这些可能性逐个排除，结论才站得住——不是「看起来没问题」，是「所有出问题的形状都没有出现」。

那 30–50 秒一帧的 output seeking 慢不慢？慢。但查案的时间按分钟计，误判回炉的时间按 52 分钟计（之二那笔 render 账），这笔 ROI 不用算。

## 三条规矩

1. **抽帧先问关键帧。** sparse-keyframe 文件上 `-ss` 放 `-i` 前会退回关键帧，296 秒能给你抽成 22.5 秒；要精确位置就 output seeking，批量加 `-nostdin`。
2. **怀疑必须变成一个可测量的量。** 「像浮层」不是结论，是报案；选一片不受干扰的 ROI，采一条像素曲线，拿曲线的起点和宽度去对源码指令——能对上的是设计，对不上的才是事故。
3. **日志级别也是工具知识。** `signalstats` 配 `metadata=print` 的结果走 info 级，`-loglevel error` 会把证据本身压掉；排查取证类命令，先确认你要看的数据在哪一级输出。

四篇到这里收口。9 分 37 秒的素材录了 5 小时、33 路抽帧崩过 16 路、30 秒缺口没补拍、一帧「浮层」查成了自家动画——这些事单看都是坑，连起来其实是同一件事：**这条管线每成熟一寸，靠的都不是更用力，而是把「我觉得」换成「量出来」。** 上屏像素要双轨探测，帧率要 ffprobe 对表，缺口要按形状开方，浮层要 300 个采样点结案。下一集 hf-05 开拍前，backlog 上还压着三星三项（音画标定片、内容寻址增量渲染、投稿幂等），规矩已经备好，按账还就是了。
