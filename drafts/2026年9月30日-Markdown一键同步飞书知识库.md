## 小白交底

先把这一篇要解决的事摊开：

1. 叶扬想把一批本地 Markdown 草稿搬进**飞书知识库**，好在手机上随时审稿。飞书明明支持「导入 Markdown」，听起来一条命令的事。
2. 结果第一次导入就被泼了冷水：**正文里的本地图片全部变成裂图占位，Mermaid 图表原样变成一段代码，完全不渲染**。
3. 翻官方文档、搜网上教程，都没有现成解法。这两个坑，飞书的导入功能压根没打算帮你填。
4. 最终叶扬用飞书官方命令行工具 lark-cli 写了个同步脚本：先正常导入成在线文档，再做一遍**块级「装修」**——把占位图块替换成本地图，把 Mermaid 代码块替换成飞书白板。
5. 本以为装修完就收工，可这套流水线在后续几十篇的实战里又逼出三堂课：**白板对 subgraph 的支持比想象中更脆、手机端要另配一条大字图通道、几十篇文档得有一个 MOC 总入口**。
6. 过程里还顺手填了三个 Windows 专属的坑。最后做到一条命令、幂等同步，图片和流程图在手机上都正常显示。

一句话：**飞书的 Markdown 导入只给你一套「毛坯房」，图片和图表要靠块替换自己装修；装修完之后，手机端的可读性和知识库的组织方式还得再上一层楼**。这篇把整套做法、全部坑点和脚本结构一次讲清。

## 一、为什么要把 Markdown 搬进飞书

先说背景，这套方案不是凭空折腾出来的。

叶扬平时写系列文章，习惯在本地用 Markdown 起稿，再放到一个 docsify 草稿审稿站上看效果。docsify 是个跑在本地（或自己服务器）的轻量文档站，电脑上看很方便。可一旦人在外面、只想拿手机审稿，就麻烦了：本地服务连不上，而原先依赖的线上托管又恰好出了意外（账号层面的问题，与本篇无关）。

于是需求变得很具体：**找一个随时能在手机上打开、排版稳定、还支持中文文件夹的地方放草稿**。飞书知识库正好合适——它有目录树、手机端体验好，而且官方提供了开放 API 和命令行工具，能自动化。

目标定了：写一个脚本，把本地一批 `.md` 文件，连同里面的图片和 Mermaid 图，一键同步进飞书的某个知识库。写完或改完，跑一下，手机上就是最新版。

## 二、第一次导入：一盆冷水

飞书（以及它的命令行 lark-cli）支持把 Markdown 导入成在线文档，类型是 `docx`。命令大致是这样：

```bash
lark-cli drive +import --file draft.md --type docx --name "文章标题"
```

导入成功，文档也生成了。叶扬兴冲冲点开——然后看到两处刺眼的问题。

**第一处：图片全裂了。** 正文里原本写的是相对路径引用的本地图：

```markdown
![示意图](images/card.png)
```

导入之后，这些图统统变成同一个占位图块，内部名字是 `default.png`，页面上就是一个打不开的空框。原因不复杂：导入是在飞书的服务器上发生的，服务器拿不到叶扬电脑里的本地图片，又不能凭空猜，只好放一个占位块顶上。

**第二处：Mermaid 没有渲染。** 叶扬的文章里大量用 Mermaid 画流程图（就是那种用文本描述节点和箭头、自动生成示意图的工具）。导入后，这些图没有变成图形，而是原封不动保留成一个代码块（`<pre><code>`），手机上看就是一大段 `flowchart TD ...` 的源码。

也就是说，**导入只搬运了文字，图片和图表这两类「视觉内容」全都丢了**。对一个讲究图文并茂的系列来说，这等于没法用。

![官方 Markdown 导入的两个硬伤：图片占位、Mermaid 变代码](/screenshots/feishu-pain.png)

## 三、思路：导入是毛坯，块替换是装修

盯着这两个坑看了一会儿，叶扬想明白了一件事：**不必指望「导入」一步到位，而要把它拆成两段**。

- **第一段：导入出毛坯。** 不管图片和图表，先让飞书把文字、标题、表格、列表这些它擅长的东西，老老实实导成一个在线文档。这一步官方做得很好。
- **第二段：块级装修。** 导入后的文档，本质是由一个个「块」（block）组成的：标题块、段落块、图片块、代码块……每个块都有自己的 id。只要能拿到这两个「问题块」的 id，就能用块替换命令，把占位图块换成真正的图、把 Mermaid 代码块换成能渲染的白板。

整套流水线于是变成这样：

```
本地 Markdown
   │  ① 写入临时文件
   ▼
drive +import  ──→  在线文档（docx，毛坯：文字齐全 / 图裂 / Mermaid 是代码）
   │  ② wiki +move
   ▼
挂到知识库（出现在目录树里）
   │  ③ docs +fetch --detail with-ids
   ▼
拿到所有块的 id，定位「占位图块」和「Mermaid 代码块」
   │  ④ docs +update --command block_replace
   ├──→ 占位图块  ⇒  本地实拍图（<img path=...>）
   └──→ Mermaid 块 ⇒  飞书白板（<whiteboard>，自动渲染）
```

同步脚本 `tools/feishu-sync.py` 干的就是这五步，外面只暴露一条命令：

```bash
python tools/feishu-sync.py 草稿A.md 草稿B.md
```

而且整个过程是**幂等**的：每次同步前先删掉知识库里同名的旧文档，再重新导入、装修。所以同一篇跑多少遍、改多少版，知识库里始终只有一份最新的，不会越积越多。

## 四、第一个坑：把占位图块换成本地图

先解决图片。关键是搞清楚两件事：怎么找到那几个占位块，以及拿什么把它们换掉。

### 怎么定位占位块

导入挂库之后，用这条命令把文档「连同块 id 一起」取回来：

```bash
lark-cli docs +fetch --doc <文档token> --detail with-ids
```

返回的是一份带 id 的类 HTML 内容。占位图块长这样，块上挂着 `name="default.png"`：

```html
<img id="块ID" ... name="default.png" ... />
```

脚本用一个正则，把所有这种 `default.png` 的图片块 id 按文档顺序收集起来。巧的是，源稿里的图片引用顺序和这些占位块的顺序是一一对应的——源稿第一张图，对应文档里第一个占位块。所以把「源稿图片路径列表」和「占位块 id 列表」按下标两两配对，就能逐个替换，不会错配。

### 拿什么换掉它

替换用的是块更新命令 `block_replace`，新内容用 `<img>` 标签，并通过 `path` 指向仓库里的本地文件：

```bash
lark-cli docs +update --doc <文档token> \
  --command block_replace --block-id <块ID> \
  --content '<img path="@./static/screenshots/card.png" width="620"/>'
```

这里有两个要点：

- `@./` 开头的路径，告诉 lark-cli 这是一个**随命令上传的本地文件**（相对于仓库根目录），而不是一个网址。lark-cli 会先把文件传上去，再让图片块引用它，图就正常显示了。
- 源稿里写的是 `/screenshots/card.png`，脚本自动把它映射到仓库里的 `static/screenshots/card.png`，再拼成上面的 `@./` 路径。约定一致，就不用每张图手动改。

叶扬试过另一条直觉路径——先用媒体上传接口把图传上去、拿到文件 token，再让图片块引用它。结果上传虽然成功，图片块的引用却纹丝不动，fetch 回来还是占位块。所以最终老老实实用 `block_replace` 整体换掉，反而一次成功。

## 五、第二个坑：把 Mermaid 代码块换成白板

图片搞定，再来啃图表。飞书里能渲染图形的容器是**白板**，而 Mermaid 正好是白板支持的一种类型。

### 基本替换

和图片同样的思路：fetch 出所有代码块，挑出里面是 Mermaid 的（特征是含 `flowchart TD` 这类关键字），拿到块 id，再用 `block_replace` 把内容换成一个 Mermaid 白板：

```html
<whiteboard type="mermaid">
flowchart TD
  A["节点一"] --> B["节点二"]
</whiteboard>
```

飞书收到后会自动把它渲染成一张真正的流程图，手机上点开还能缩放、编辑。这一步替换本身不难，**真正费功夫的是「格式翻译」**——Mermaid 在 Markdown 里的写法，原样塞进白板会出问题，得做三处处理：

1. **去掉主题配置指令。** 叶扬的 Mermaid 开头都有一段 `%%{init: {...}}%%`，那是用来指定暗色主题的（画布、节点配色等）。飞书白板不认这个，留着会导致解析失败，必须整行删掉。
2. **把 `<br/>` 换成空格。** 节点文字里原本用 `<br/>` 换行，白板的 Mermaid 解析器对此处理不一致，稳妥做法是统一替换成空格，让文字在一行里显示。
3. **subgraph 周围全是雷（这个坑最隐蔽，而且不止一种）。** 见下。

### 最隐蔽的坑：白板与 subgraph 的三种雷区

叶扬有一些图用了子图（`subgraph`，把几个节点框进同一个分组）。在后续几十篇的实战里陆续发现：**只要图里出现 subgraph，就有三种写法会让白板报同一组错误**——

```text
degrade_code=2107, Whiteboard content parse failed
degrade_code=1003, Instruction produced empty content after transform
```

**雷区一：边直连子图本身。** 最容易想到的一种，让箭头直接连在子图 id 上：

```text
subgraph G["分组"]
  N1["..."]
end
A --> G
```

在普通 Mermaid 里这完全合法，意思是箭头指向整个分组。可白板解析器不认——不管是箭头指向子图（`A --> G`），还是从子图指出去（`G --> B`），都会让整段解析失败。

**雷区二：边跨越子图边界。** 这是后来批量重同步时才抓到的、更隐蔽的一种。边的两端都不是子图 id，而是「外面一个节点、子图里面一个节点」：

```text
subgraph G["分组"]
  N1["..."]
end
A --> N1
```

语法上看毫无问题——箭头连的明明是具体节点 N1。可在白板解析器看来，这条边**从子图外部跨入了子图内部**，照样让整段转换失败，还是 2107＋1003。它最坑人的地方在于：Mermaid 官方渲染、肉眼看图都完全正常，只有飞书白板不答应，排查时根本不会往这儿想。

**安全岛：要进白板的图，干脆不用 subgraph。** 踩过两轮之后，叶扬定下一条笨但稳的规矩：正文概念图一律不用 subgraph——想表达分组，就让组内成员各自独立成节点，在节点文字里写明归属（比如几个节点都以「管控：」开头），分组关系靠文字并列。中系后面十几张图全部按此重构，再没出过一次 2107。

需要补充一句：**subgraph 本身白板是支持的**，子图能正常渲染；出问题的始终是「边」与子图边界的关系。如果图简单、边全在各组内部活动，用 subgraph 无妨；一旦边要跨组，拿不准时，不用最省心。

脚本里那道**兼容性自检**（转换前收集子图 id、逐行扫描边的端点，命中子图就打印行号警告）只能拦住雷区一；雷区二的跨边界边两端都是普通节点，静态扫描很难识别，只能靠「不用 subgraph」从根上绕开。这也是自检的已知边界，不能全指望它。

![白板 subgraph 三种雷区：直连、跨边界，与「不用 subgraph」安全岛](/screenshots/feishu-wb-mines.png)

### 不只是 subgraph：复杂图本身也会 2107

排查 subgraph 时做对照实验，叶扬又撞上第四种、也最让人没脾气的情况：**图里完全没有 subgraph，只是节点数一多，白板照样报同一组 2107／1003**。十几个节点的长链、分叉再汇合、带回头边（有向环），都可能失败。

更麻烦的是结果**不稳定**。同一份十几节点的代码，前一天在某个文档里替换成功（白板至今好好的），第二天原样导入另一个文档却失败；同样六个节点，在不同文档里一成一败。另外，节点 id 写成带数字的（`N1`、`A1`）时更容易失败，而用纯字母的语义 id（`HAN`、`SONG`、`TAI`）最稳。

这些现象合起来说明一件事：**飞书白板内置的 Mermaid 解析器，有一个不高、而且会抖动的「复杂度容忍度」**。它不是完整的 Mermaid 实现——「这语法在官方 Mermaid 里合法」不等于「白板一定渲染得出」。节点数量、分叉、环、id 形态，都会把它推过临界点。

所以最终的分工策略，比「图都塞白板」更细一层：

- **几个节点的简单线性小图**：放心用白板，手机上还能点开编辑；
- **节点多、有分叉或环、结构复杂的图**：别赌白板，改走下一章的 mermaid.ink 渲染成静态 PNG，结果稳定、版式也可控。

本篇第九章那张「脚本内部结构图」就属于复杂图——你在那里看到的不是白板，而是一张 PNG，原因正是这里。

### 文档已建好、只有 Mermaid 失败时怎么办

实际操作中还遇到一种情况：图片在前面已经替换成功，脚本却在替换 Mermaid 时抛错中断，留下一个「图都正常、就差一张流程图」的文档。这时不必整篇推倒重来——写一个小脚本，对这个文档重新 `fetch --detail with-ids`，会发现残留的占位图块是 0、只剩一个 Mermaid 代码块；拿到它的块 id，单独做一次 `block_replace` 补上即可。哪坏修哪，是幂等流程的好处。

## 六、手机端二次优化：用 mermaid.ink 生成大字 PNG

白板替换成功之后，手机审稿又暴露一个新问题：**白板是「可编辑图形」，不是为阅读优化的静态图**——节点一多，手机上默认缩成一团，要双指放大、来回拖动；而叶扬另一类配图（HTML 卡片导出的 PNG）是按电脑屏幕尺寸排的字号，发到手机上，文字小了得凑到眼前看。

诉求于是变得很明确：**想要一张暗色底、大字号、纵向排布、手机点开就清清楚楚的静态 PNG**，而且最好仍由 Mermaid 文本生成，改起来方便。

最后找到的通道是公开服务 mermaid.ink：把 Mermaid 代码连同主题配置打包成一个 state，压缩、编码后拼进 URL，直接请求就返回 PNG。配套写了个小工具 `tools/mermaid-shot.js`，吃一个 spec 文件（多张图的代码与宽度），批量出图：

```text
https://mermaid.ink/img/pako:<编码串>?type=png&width=900&bgColor=dark
```

编码和参数这一步有四个实测出来的坑：

1. **压缩必须用带 zlib 封装的 deflate，不能用 raw deflate。** state 是一个 JSON（Mermaid 代码＋暗色主题变量），先做 `zlib.deflateSync` 压缩，再做 URL 安全的 base64（base64url），前面加 `pako:` 前缀。叶扬起初用了 `deflateRawSync`（没有 zlib 头尾的裸 deflate），服务端一律返回 400——前缀既然叫 pako，要的就是 pako 库默认那种带 zlib 封装的 deflate。
2. **`scale` 不能单独使用。** 想提分辨率加个 `scale=2`，服务端报错「scale can only be set when either width or height is set」；配上 `width`（或 height）才生效。
3. **十六进制的 `bgColor` 同样不能单独用。** `bgColor=0d1117` 单独出现时报 400（服务端参数校验的 bug）；要么和 width 一起给，要么干脆写 `bgColor=dark`。
4. **默认 PNG 是透明背景。** 暗色主题里的浅灰箭头落在飞书白色文档底上几乎隐形，所以必须强制指定深色底。

这条通道与白板是**分工**关系：要在飞书里点开缩放、协作编辑，走白板；要手机端阅读体验最好、版式完全可控，走静态 PNG。中系收官阶段的十几张概念图全部改成纵向大字版之后，手机上终于不用再放大看字了。

## 七、知识库成型：一篇 MOC 当总入口

同步了几十篇之后，又冒出一个「幸福的烦恼」：知识库目录树是平的——文档按标题一篇篇排列，刚进来的读者（以及一周后的自己）打开手机，**看不出该从哪篇开始、各篇之间是什么关系**。

解法是把系列的开篇那篇，改造成一个 **MOC（Map of Content，内容地图）**：

- 开篇原有的概述内容照常保留；
- 文末放一张全系列路线表，每个标题直接做成超链接，指向该篇在飞书里的 docx 网址；
- 用记号区分状态：已发布、已定稿待发、计划中。

手机上打开 MOC，点任意标题就跳进对应文档，几十篇知识库文章就此能当一本书从头翻。这个 MOC 本身也走同一个同步脚本，配图、白板一次到位。

**这里还藏着幂等设计的一个盲区：改标题会留下旧节点。** 脚本同步前是按「标题完全相等」去找旧文档、删旧重建的。如果某次把文章标题改了（比如事后补齐编号），旧标题那篇不会被认出来，于是新旧两篇同时挂在知识库里。叶扬做标题统一时就撞上了：解决办法是跑一个小清理——先列出知识库全部节点，把旧标题的节点显式删除，再同步新标题。所以记住：**幂等只对「标题不变」成立；标题一旦变动，要手动清理一次旧节点。**

![MOC 模式：一页总目录链接全系列；改标题后须手动清旧节点](/screenshots/feishu-moc.png)

## 八、Windows 上的三个专属坑

思路在任何系统上都一样，但叶扬是在 Windows 上跑的，这里额外有三个坑，值得单独说，免得同样环境的读者重走弯路。

**坑一：不能直接跑那个没有扩展名的 lark-cli。** Windows 上同名的可执行入口有好几个，Python 用 `subprocess` 直接去跑无扩展名的 `lark-cli`，会报一个经典错误——`[WinError 193] %1 不是有效的 Win32 应用程序`。因为那是个 shell 脚本，不是 Windows 可执行文件。

**坑二：也别走 `.cmd` 包装。** 那为什么不用 `lark-cli.cmd` 呢？因为替换用的内容里大量含有 `<img ... />`、`<whiteboard>` 这类尖括号。参数一旦经过 `.cmd` / cmd.exe 这一层，`<`、`>` 会被当成命令行的输入输出重定向符号，命令就乱套了。

**最终办法：绕过这两层，用 node.exe 直接跑 lark-cli 的 JS 入口。** lark-cli 本质是个 Node 程序，安装目录下能找到真正的入口脚本（`node_modules/@larksuite/cli/scripts/run.js`）。脚本里用 `node.exe run.js <参数>` 的方式直跑：既绕开了 WinError 193，也不经过 cmd 的重定向解析，尖括号参数安全到达。

**坑三：`auth status` 的返回里没有顶层 `ok` 字段。** 脚本里封装了一个统一的调用函数，默认会检查返回 JSON 的 `ok` 字段是否为真。可查询登录状态的 `auth status` 命令，返回结构里压根没有顶层 `ok`，于是被误判成失败。解决办法是给这个调用加一个开关：查登录状态时不要求 `ok`，改为直接看用户身份是否可用——`available` 为真，且 token 状态属于 `valid`、`ready`、`needs_refresh` 之一。这里又有个小细节：状态偶尔是 `needs_refresh`，但只要 `available` 为真，lark-cli 会在下一次用户 API 调用时自动刷新，照样能用，不该被当成「未登录」拦下。一个小例外，却能避免把「其实已登录」误读成「未登录」。

## 写在最后

这套工具最初是为「手机审稿」这一个很实际的需求写的，写完之后反而成了叶扬现在最顺手的同步通道：本地改稿，一条命令，手机上立刻是图文完整的最新版，不再受本地服务和线上托管状态的牵制。

回头看，最初那四个坑里有一个共同规律值得记下：**遇到「官方一键导入」这类黑盒，不要在黑盒里反复试参数，而要往后退一步，看清它产出的东西的结构**。飞书文档是一个个有 id 的块，看清这一层，占位图和死代码就不再是「导入失败」，而是两个明确等着被替换的块。把黑盒拆成结构，问题往往就从「没法办」变成了「替一下就好」。

而再往后的三堂课——白板的边界、大字图通道、MOC 入口——则指向另一件事：**真正的交付物从来不是「同步成功」，而是「读者在手机上读得舒服、找得到路」**。工具跑通只是起点，用得越久、离真实读者越近，要补的课就越具体：不是「能不能显示」，而是「字够不够大」；不是「文档在不在」，而是「从哪一篇开始」。这层意识，比脚本本身更值得带走。

脚本里涉及的密钥、身份标识都放在独立的配置文件里、不进版本库；本篇展示的命令也对这些信息做了虚化。如果读者照着搭，记得把自己的密钥照同样方式收好，别提交进公开仓库。
